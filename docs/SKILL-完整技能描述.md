# SKILL 完整技能描述：把一句模糊的话，定型成一份可验证的技能定义

---

## 它是什么

这是一个负责「定型」的技能。输入通常只有一句话——「我每周都要整理这个客户反馈表，能不能让 AI 帮我弄」；输出是四件可以拿去用的东西：一张需求卡、一份写定并验过的检索入口、一组验收标准、一份待确认清单。

它不生产最终成品，也不替人做业务判断。它只做一件事：**在那句话还含糊的时候，把边界钉死，让它变成后面每一步都能直接引用的确定输入**。

之所以需要这样一道定型，是因为有一群人想把自己的经验固化下来，却不知道从哪下手。他们缺的不是知识，是一条能照着走、每一步都知道「做到什么算过」的路。而这条路最容易在起点就走歪：脑子里刚有画面，就直接开始动手写，写着写着范围越来越大——今天想让它教人写描述，明天想让它帮人诊断线上故障，后天又想让它顺带把发布流程也管起来。最后做出来的东西什么都能干一点，什么都不精，人拿在手里不知道什么时候该用它，模型检索的时候也不知道该在什么场景下召回它。

定型要防的就是这个。它在动笔之前先把六件事问清楚并写下来：**服务谁、解决什么问题、用户会怎么开口、交付什么、明确不做什么、做到什么程度算合格**。这六件事写死了，后面的事都是体力活；这六件事含糊着，后面每一步都会反复推翻重来。

边界一旦写死，还有一个附带好处：拒绝变得容易。有人提出「能不能顺带把某件事也管了」，只要对照「不做什么」那一栏，一句话就能判断该不该收，不需要重新讨论一遍方向。反过来，边界没写死的时候，每一个新想法都像一次改进，直到某天回头看，已经认不出最初要解决的到底是什么问题。范围不是被一次扩张撑坏的，是被一连串看起来都很合理的追加慢慢泡软的。

## 一次完整的运转

把规则连起来，一次完整的运转是这样的。

一句话进来，先不急着动笔。技能先声明自己走哪条线——是把模糊需求定型，还是给已经做出来的东西找毛病——并当场点明四类信息是否齐全：对方原话、发生的场景与频率、想要的交付物、明确不做的边界。缺哪项就明说缺哪项，不猜。

接着采集。两轮、每轮不超过三问，第一轮只围绕对方会怎么开口、这件事多久发生一次、最后想拿到什么形态的东西；第二轮才问最不希望被什么触发、哪些情况看着像该用其实不该用、有没有必须遵守的规则。答案已经够填某个字段时，那个字段就不再问。

八个字段齐了，才写检索入口。三段一次写完，当场核对人称、长度、原话条数、可识别对象、排除场景，再对一遍禁词表。写完不放着，立刻拿三种说法各试一次：口语的、点名术语的、完全不提术语只说痛点的。三条都命中才算定稿；有一条落空，就停在原地补原话，补完三条从头再测一遍。

入口定稿之后才写验收标准，三到五条，每条都能用一个动作验证，覆盖能不能被触发、能不能被执行、结构合不合格、边界清不清楚。最后把需求卡、入口定稿与测试记录、验收标准、待确认清单四样一起摆出来。

整条动线只有一个规矩贯穿始终：**任何一环没过，就停在那一环，不带着半成品往下走**。看着慢，实际省掉了后面反复推翻的时间。含糊如果不在入口被拦住，就会一路流到产出里，变成谁也说不清对不对的东西。

## 为什么「想清楚了」不算数，必须写下来

心里想的和写下来能执行的，是两回事。

心里想的时候，人会自动补全模糊的地方。觉得「帮用户做技能」这句话很清楚，真到落笔才发现它什么都没说：帮谁做？做哪一种？用户说什么话的时候该用？产出是什么形态？这些问题在心里会自动滑过去，写的时候滑不过去。

更关键的是，定型的结果决定了后面所有验证的基准。检索入口写得好不好，靠的是需求卡里有没有留着用户原话；文件结构该不该加东西，靠的是需求卡里有没有「需要脚本保证确定性」这类要求；正文里每个动作的回头条件从哪来，靠的是需求卡里写下的边界和反例。定型是空的、模糊的，后面每一步都在猜；猜错了，就得整体返工。

所以它不是一个形式上的过场，而是整条链的**输入源**。它做扎实了，后面是流水线；它做虚了，后面是打地鼠。

还有一层更隐蔽的原因：写下来的东西可以被别人反驳，留在心里的不能。需求卡摊开，哪一条是原话、哪一条是推断、哪一条还没拍板，一目了然；含糊留在脑子里，谁都说不清分歧到底在哪，直到产出对不上才开始互相追问。把含糊逼成文字，本质上是在让分歧提前暴露，而不是等它变成返工。这也是为什么「触发原话」和「不做什么」两栏不许概括、不许术语化——一旦被润色成漂亮的书面语，可核对性就没了，谁都能按自己的理解往里填。

## 产出规格：四件东西，缺一不可

**第一件，需求卡。** 八个字段，把来龙去脉固定住：服务对象、真实场景、触发原话、目标产出、关键约束、不做什么、相邻易混淆需求、待确认项。其中「触发原话」和「不做什么」两栏必须保留用户原话措辞，不概括、不术语化——它们是后面写检索入口和排除场景的直接素材。

**第二件，检索入口定稿。** 这是唯一常驻在检索上下文里的字段，决定这个技能有没有机会被用上。它要同时回答三件事：做什么、什么时候用、不覆盖什么。写完必须用三种不同说法各测一次，三种都命中才算定稿。

**第三件，验收标准。** 三到五条，写清楚什么样的产出算合格。这不是给别人看的，是给自己后面每一步做判断用的尺子：正文要不要给每个动作写回头条件，看标准里有没有要求「可复现」；自检某一条过不过，看标准里有没有对应判据。

**第四件，待确认清单。** 推断出来的、需要人拍板的、暂时按某种默认处理的，全部列进来。每条写清三件事：确认什么、不确认的后果、当前默认取什么。

## 需求卡：八个字段逐个说清

**字段一，服务对象。** 不写「所有人」，写清楚具体哪一类人。常见的三类各有各的卡点：业务专家对领域了如指掌，知道一份合格的尽调报告要看哪七个维度，但不懂技术，不知道「描述」和「指令」的区别，容易把技能写成一篇经验总结——读起来很有道理，执行起来没有步骤；一线执行者被重复劳动困住，清楚自己每天在重复什么，却说不清「这件事的规则是什么」，问他怎么判断该不该退，他说「看情况」；半懂技术的人看过几篇文章，知道有元数据、有渐进加载、有脚本，于是热衷于把结构做得很专业，主文件里却全是「请专业地分析」「酌情处理」。

写清服务对象的用处很直接：后面所有内容的语气、详略、举例方式都由它决定。服务业务专家，就多讲「怎么把经验变成步骤」；服务半懂技术的人，就多讲「为什么不该一上来建四个目录」。

**字段二，真实场景。** 不写「用户想做技能的时候」，写一个能想象出画面的具体场景。比如「一个运营每周要整理客户反馈表，每次都要重新想一遍归类逻辑，想找个办法固定下来」。场景要有角色、有频率、有痛点。越具体，后面写产出示例越有素材。

**字段三，触发原话。** 八个字段里最重要的一个。要收集的是人真的会说的话，不是你觉得他会说的话。区别很明显：「帮我创建一个 Agent Skill」是设计者会说的话，「我想做个东西让 AI 帮我干这个活」才是用户会说的话。收集方式是想三个不同的人会怎么开口——一个懂术语的、一个完全不懂的、一个半懂不懂的——三句话原样记下来，不改写。这三句后面会直接变成检索入口里的触发语，也会直接变成三种说法测试的三条用例。

**字段四，目标产出。** 具体到形态：是产出一个文件，还是一个完整的目录结构，还是一个能直接分发的包？里面必须包含什么、可以包含什么、不该包含什么，都要写清楚。这一栏直接决定了文件结构的最小集是什么。

**字段五，关键约束。** 必须遵守的规则，三五条就够，但每条都要能判定。写「要专业」不是约束，写「不用第二人称、不用营销词」才是约束；写「质量要高」不是约束，写「引用的每个文件路径都真实存在」才是约束。典型的三条是：产出必须能被另一个模型在不看别处的情况下照着执行；主文件不超过三百行；检索入口必须包含用户原话。

**字段六，不做什么。** 这一栏和「做什么」同样重要，甚至更重要。一个技能的边界，一半靠它做什么定义，一半靠它不做什么定义。要写清三类：能力上不做，比如不覆盖平台界面操作和账号授权；场景上不做，比如不为一次性任务封装；判断上不做，比如不替人决定这个技能该不该上线。每一类都给一句理由，理由是后面写排除场景的素材。

**字段七，相邻易混淆需求。** 有哪些需求看起来像该用它、其实不该。比如「帮我把这段文字翻译一下」，看起来是让 AI 干活，但它是单步操作，不该固化成技能。列出这类需求有两个用处：一是写排除场景，二是给「先判断该不该做」那个动作提供判据。

**字段八，待确认项。** 想不清楚的、需要人拍板的、暂时按某种默认处理的，全部列在这里。不许因为想不清楚就不写，也不许自己替人决定了却不标出来。

## 八个字段怎么来：两轮采集，每轮不超过三问

不许自己编。触发原话和「不做什么」这两栏几乎不可能靠推断得到，必须问。

采集分两轮，每轮不超过三个问题。第一轮只问和触发有关的事，因为触发原话是地基，地基没打就先问别的，容易问偏：

1. 你或者你的同事，平时会怎么开口说这件事？给我原话，越随意越好。
2. 这件事大概多久发生一次，是谁发起的，通常在什么样的对话里发生？
3. 你希望最后拿到的东西是什么样子，是一个文件、一个文件夹，还是别的？

第二轮问交付和边界：

1. 这个东西做出来之后，你最不希望它在什么情况下被触发？
2. 有哪些看起来像该用它、但其实不该用的情况？
3. 有没有哪些规则是你觉得必须遵守、不遵守就不行的？

答案填进八个字段。凡是推断出来的、不是明说的，全部标上「推断」两个字。推断项不阻塞产出，但交付时要一次性列出来请人确认，不能混在确认项里蒙混过去。

有一条硬规矩：给到的信息已经够填某个字段了，就不再问那个字段。不许为了走流程把已经知道的事再问一遍，那是对人时间的浪费，也是不专业的表现。

## 一份填好的需求卡长什么样

以「我每周都要整理这个客户反馈表」为例，八个字段填完是下面这个形态。它存在的意义不是好看，是让后面每一段文字都能从表里找到出处：

| 字段 | 内容 |
| --- | --- |
| 服务对象 | 一线运营，被每周重复劳动困住，能说清自己烦什么，但提炼不出归类规则 |
| 真实场景 | 每周一上午把上周客户反馈按问题类型归类，每次都要重新想一遍「这条算投诉还是建议」，耗时约一小时 |
| 触发原话 | 「整理这周的客户反馈」「把这个表归类一下」「每周都要重新想一遍，能不能固定下来」「我想做个东西让 AI 帮我干这个活」 |
| 目标产出 | 一份 `feedback-triage/SKILL.md`，必含：归类维度表、每类的判定条件、无法归类时的处置、输出文件格式与必含字段 |
| 关键约束 | 不用第二人称与营销词；主文件 ≤300 行；每个归类维度必须给出可判定的条件句，不许写「酌情判断」 |
| 不做什么 | 能力上：不覆盖平台界面操作与账号授权；场景上：不为一次性的临时表格固化规则；判断上：不替使用者决定哪类反馈需要升级给主管 |
| 相邻易混淆需求 | 「帮我把这段英文翻成中文」（单步操作）、「统计这个月退款总额」（另一次性的数据查询）、「帮我排一下发布流程」（属于运营治理） |
| 待确认项 | ① 归类维度是否固定为这四类 → 不确认会导致维度每次漂移 → 当前默认取四类；② 输出是否落盘到固定目录 → 不确认会导致产出位置不一致 → 当前默认只在对话中给出 |

两处细节值得留意。「触发原话」一栏保留了「我想做个东西让 AI 帮我干这个活」这种完全不通顺、但确实会被说出口的句子，没有改成「创建一个 Agent Skill」；「不做什么」一栏三条各带理由，这些理由后来会直接变成检索入口里的排除场景。表里没有一处写着「提升效率」「智能化」这类词，因为它们填进去也判断不了任何事。

推断项单独标出，不混在已确认内容里。上表的「耗时约一小时」若非本人明说，就要带「推断」标记，并在交付时列入待确认清单。

## 检索入口：三段，缺一不可

需求卡填完，写检索入口的素材就齐了。结构固定三段，顺序可以调，三段不能少。

**第一段，做什么。** 动词开头，说清楚产出什么。不写「帮助用户」「辅助用户」，直接写动作和对象。「把一句模糊需求变成可用的技能定义」是合格写法；「帮助用户创建技能」不合格，因为「帮助」是空词，没增加任何信息。

**第二段，什么时候用。** 这一段是灵魂，也是绝大多数技能死掉的地方。要包含两样东西：触发场景的描述，和至少三条用户原话。原话用引号包起来，让检索时能精确匹配；场景描述要说清在什么任务、什么对话里该用它。

**第三段，不覆盖什么。** 写清边界，防止误触发。这一段经常被省略，代价是到处抢活——人问个翻译它也跳出来，查个资料它也跳出来，最后被关掉了事。排除场景要具体：写「不覆盖平台界面操作和账号授权」，不写「不适用于其他场景」这种废话。

三段写完，还要过五道硬关：第三人称，不出现「你」「我」；总长不超过一千零二十四个字符；至少三条用引号包住的用户原话；至少一个可识别对象，比如文件类型、任务名、领域术语；写清不做什么。

另有一张禁词表：帮助、辅助、相关、各种、提升效率、智能化、一站式。这七个词一个都不许出现，因为它们不携带任何可用于检索的信息。

## 三种说法测试：写完立刻测，不过不往下走

检索入口写完不能就放着，必须当场测。拿三种不同风格的说法去试，看能不能命中。

**口语型**：日常最自然的说法，带口语词、不精确，比如「我想做个东西让 AI 帮我干这个活」。
**术语型**：知道术语、直接点名，比如「帮我写个 SKILL.md」。
**无术语型**：完全不知道术语，只描述痛点，比如「我每次做这个都要重新想一遍，能不能固定下来」。

三条都来自需求卡里收集的触发原话，不许另编。每条都要能命中入口里的触发语，命中不了就说明缺了对应说法，补完再测。三种全中才算过，两种或一种命中都算没过。

这里有个很容易犯的错：测的时候自己心里知道答案，看着入口觉得「这句话应该能匹配上」，就判通过。这不叫测试，叫自我安慰。真正的测法是把说法单独拿出来，不看入口，只判断一个不知道上下文的人看到这句话，会不会想到用这个技能。想得到，才算命中。所以换一个人来测，或者把说法搁一天再看，往往比当场判定可靠。

还有一条硬规矩：入口一旦定稿，后面不能随便改。哪一步发现必须改，改完必须把三种说法**整体重跑**，不能只测改动涉及的那一条——因为入口是一个整体，改一个词可能影响另一条的匹配。测试记录也要留下，不许测完不留痕。

## 一份测试记录长什么样

记录要能复看，不能只留一个「通过」。下面是同一批说法留下的形态：

| 类型 | 说法（取自需求卡原话栏） | 判定 | 依据 |
| --- | --- | --- | --- |
| 口语型 | 我想做个东西让 AI 帮我干这个活 | 命中 | 入口「」内原话逐字收录，且「做个东西」落在口语场景描述里 |
| 术语型 | 帮我写个 SKILL.md | 命中 | 命中可识别对象 `SKILL.md`，且原话在入口中 |
| 无术语型 | 每周都要重新想一遍，能不能固定下来 | 命中 | 命中原话「每周都要重新想一遍」，全句不含任何术语 |

三条都来自同一张需求卡，没有另编。判定栏写的是**依据**，不是「感觉能中」；只要有一条写不出具体依据，就按未命中处理，回入口补该类原话后三条整体重测。

记录里还应有三个字段：测试日期、入口版本号、重测原因。它们看着琐碎，用处很明确——哪天入口被改了一个词，凭这三个字段就能判断旧记录还能不能算数。缺了版本号，「三条全中」这四个字过两周就失去了意义。

---

## 验收标准：三五条，每条都能判定

验收标准是给自己后面每一步用的尺子，必须写成能判定的句子，不能写成愿望。

合格的写法：「产出的技能能被另一个模型在不看别处的情况下照着执行」「三种说法全部命中」「主文件不超过三百行且无占位符残留」「引用的每个文件路径都真实存在」。每一条都能用一个动作去验证。

不合格的写法：「产出的技能质量要高」「描述要写得好」「结构要清晰」。没法验证，写了等于没写。

条数控制在三到五条。太少盖不住关键点，太多记不住、执行时会漏。要覆盖四个方面：能不能被触发、能不能被执行、结构合不合格、边界清不清楚。每个方面一条，基本就够了。

贯穿所有标准的是一句更朴素的话：**另一个模型拿到这份东西，能不能不看别处，照着做出同样的结果？** 按这把尺子，「请专业地分析」不合格，因为另一个模型不知道「专业」指什么；改成「逐条列出违约责任条款，标注触发条件和赔偿上限，缺失的标『未约定』」就合格了。「根据情况调整」不合格，因为「情况」没有判定条件；改成「当样本量小于 30 时改用 t 分布，否则用正态近似」就合格了。

---

## 一组验收标准与待确认清单长什么样

接着上面那份需求卡，验收标准写成四条：

1. 产出的技能包能被另一个模型在不看别处的情况下照着执行，每个动作都带输入、产出和回头条件。
2. 检索入口含三段，三种说法全部命中，禁词表七个词零出现。
3. 主文件不超过三百行，全文无占位符残留，引用的每个文件路径真实存在。
4. 产出文件含归类维度表、每类判定条件、无法归类的处置说明、输出文件的必含字段，四项缺一不可。

四条各覆盖一个方面：能不能被触发、能不能被执行、结构合不合格、交付物全不全。每条都有一个能立刻做的验证动作——换一个模型试跑、跑一次说法测试、数行数和扫路径、对着清单勾字段。没有任何一条是「质量要高」。

待确认清单单独成表，不混进正文：

| 确认什么 | 不确认的后果 | 当前默认 |
| --- | --- | --- |
| 归类维度是否固定为四类 | 维度每次漂移，产出无法复现 | 取四类 |
| 输出是否落盘到固定目录 | 产出位置不一致，无法验收 | 只在对话中给出，不落盘 |
| 是否要为一次性临时表格留例外 | 例外写进规则会把范围撑大 | 不留例外，一次性任务直接劝退 |

三条都不阻塞交付，但必须单列。把「当前默认」写出来是关键——它让人不需要立刻拍板也能往下走，同时清清楚楚知道哪一处是暂时替他定的。

## 常见翻车与处置

**翻车一，需求卡是自己编的。** 表现是八个字段填得整整齐齐，但触发原话一看就是术语，不像是人说的。根因是没做采集，或者采集时引导性太强，对方顺着话说了。处置：重新问第一轮那三个问题，并明确说「要原话，越随意越好」。

**翻车二，入口只有功能没有触发。** 表现是写了一大段能干什么，没有一句人会说的话。根因是把入口当成了产品介绍。处置：删掉功能罗列，只保留三段结构，把需求卡里的触发原话填进去。

**翻车三，排除场景写成了「不适用于其他场景」。** 表现是边界看起来完整，实际什么都没排除。根因是没认真填「不做什么」和「相邻易混淆需求」。处置：回到需求卡，把三类「不做」逐条写清，再从相邻需求里挑两三条写成排除场景。

**翻车四，三种说法测试自我判定通过。** 表现是记录写着三条全中，真正拿去用一条都触发不了。根因是测法反了——拿入口去套说法，而不是拿说法去试。处置：换人测，或隔一天把说法单独拿出来重看。

---

## 边界情形：遇到这些情况怎么定

规则不能只覆盖顺利的那条路。下面几种情况都会真实发生，各有确定处置，不许临场发挥：

| 情形 | 处置 | 理由 |
| --- | --- | --- |
| 只给一句话，之后不再回应 | 不阻塞；把能确定的写实，其余标「推断」并列入待确认清单，按默认取值继续 | 一句模糊需求不该被无限追问卡死，但推断绝不伪装成确认 |
| 需求本身就是一次性任务 | 明确说不建议固化，给出替代方案（一段提示词 / 一个脚本 / 一个模板 / 直接做一次） | 固化的成本高于收益，还会占掉检索名额 |
| 三种说法始终有一条不中 | 补原话重测；仍不中，回到需求本身核对「这类人是不是真该由这个技能服务」 | 反复补词无效，往往说明服务对象定错了 |
| 交付后需要改检索入口 | 改一个字也把三种说法整体重跑，记录新版本号与重测原因 | 入口是整体，局部改动能影响另一条的匹配 |
| 用户要求的边界互相矛盾 | 两条都原样保留，列出冲突点请人拍板，不擅自取舍 | 矛盾本身是待确认项，替人抹平等于替人做了业务判断 |
| 相邻需求看着很像但不该接 | 按「不为一次性任务固化」「不覆盖平台操作」等已写死的边界直接回绝 | 边界写下来的价值，就在于此刻不需要重新讨论 |
| 测试资产、报告、回归用例要放哪 | 与技能包平级独立存放，不进技能包 | 分发包要能被单独拿走使用，不该夹带开发期的东西 |

共同点只有一个：**每种情形都有写明的结果，没有「看情况」**。含糊不是被消灭的，是被一条条具体规则挤掉的；留学一个「酌情」，就等于把当初想清楚的边界又还了回去。

另外要分清两件事：需求不清可以带着推断往前走，边界不清不行。前者有默认取值兜底，后者会让后面每一步都失去判据——所以「不做什么」和「相邻易混淆需求」两栏空着时，宁可停下来问，也不许带着空栏往下写。

## 几个词在这份描述里的确切意思

同一份文档里，词的含义必须固定，否则规则会被读成另一种规则：

| 词 | 这里专指 | 不指 |
| --- | --- | --- |
| 技能 | 一个可被检索、被加载、照着执行的独立单元 | 某平台的界面功能、一段普通提示词 |
| 检索入口 | 唯一常驻检索上下文、决定能否被用上的那段描述 | 产品介绍、能力清单、宣传语 |
| 触发原话 | 人真的会说出口、原样留存的句子 | 整理过的书面语、设计者以为用户会说的话 |
| 命中 | 把说法单独拿出来，一个不知上下文的人会想到用这个技能 | 写的人自己看着入口觉得「应该能匹配」 |
| 可判定 | 存在一个动作，做完就能得出是非结论 | 「质量高」「结构清晰」「专业」 |
| 推断 | 非本人明说、由上下文补出、必须带标记的内容 | 已确认信息、可以悄悄当结论用的猜测 |
| 待确认项 | 需要人拍板、且写清了后果与默认的事 | 含糊其辞的遗留问题 |
| 边界 | 「做什么」加「不做什么」共同划出的范围 | 只写能力、不写排除的半张卡 |

把口径固定下来有个实际好处：后面的自检六问、运行约束、交付形态，用的都是这几个词，不需要在每一处重新解释一遍。读的人拿不准时，回这张表对一下就能定。

---

## 运行约束

1. 不许跳过采集直接填需求卡；触发原话和「不做什么」必须来自本人，不许推断。
2. 不许把推断项当成确认项；所有推断都要标出来，交付时单列。
3. 需求卡没定稿，不许写入口；输入没定，输出必错。
4. 入口里不许出现禁词表的七个词。
5. 入口里不许少于三条用户原话。
6. 三种说法测试不许自我判定，不许只测一条，不许测完不记录。
7. 验收标准不许写成无法判定的愿望。
8. 不许把待确认项藏起来；每条都要写清确认什么、不确认的后果、当前默认。

## 自检：输出前过一遍

一问，需求卡八个字段是不是都填了，触发原话和「不做什么」是不是保留了原话措辞？
二问，推断项是不是都标出来了，是不是单独列了一份待确认清单？
三问，入口是不是三段齐全、五道硬关全过、七个禁词零出现？
四问，三种说法是不是都来自真实原话、是不是全部命中、测试记录是不是留下了？
五问，验收标准是不是三到五条、每条都能判定、四个方面都覆盖了？
六问，常见翻车是不是写了、每条是不是都有处置方式？

六问全过，方可输出。任一不过，回到对应部分。

## 交付形态

四样东西一起给，缺一不可：需求卡，八个字段完整、推断项标注清楚；检索入口定稿，附三种说法的测试记录；验收标准，三到五条；待确认清单，逐条写清确认什么、后果是什么、默认取什么。

交付时不许只说「已完成」，要把四样实际内容摆出来。看完的人能直接说「可以」或者「这里不对，改」，这才叫交付完成。四样东西之间还各有分工：需求卡负责留住原话，入口定稿负责被检索到，测试记录负责证明它确实能被检索到，验收标准负责让后面的每一步有尺子可量，待确认清单负责把没拍板的部分隔离出来，不让它悄悄混进已确认的内容里。少给任何一样，都会在某个环节重新变成猜测。

---

说到底，这套规则想守住的只有一件事：**不让含糊混进后面任何一步**。一句话进来，四样确定的东西出去；每一样都能被下一个人拿去直接用，也能被拿去验证。至于谁在用它、它最后会被做成什么样，都不该靠猜来补。猜出来的东西看着漂亮，用起来全是窟窿；写下来的东西看着朴素，交出去才站得住。

这也解释了为什么整套规则里到处都是「不许」和「必须」：它们不是姿态，是把判断提前固化下来。真正难的不是写出一份漂亮的说明，而是在每个容易滑过去的地方，都留下一句能被别人核对的话。做到了这一点，哪怕换一个人、换一个模型接手，结果也不会走样。
