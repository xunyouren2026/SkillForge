# skill-creator｜AI Skill 创建器：它是什么、调用后做什么、能干什么

> 文档性质：项目说明（背景解释 + 功能说明 + 现状交代）。
> 写作依据：项目组的背景描述重写，以及早期四路外部调研与《汇总与背景校验报告》。
> 缺口说明：四路调研报告未随仓库提供，本说明中引用的外部事实无法逐条复核，引用处请按二手口径对待。
> 口径声明：文中关于项目自身的数字全部来自真实执行的校验输出与只读统计，无估算、无预填；涉及外部世界的事实标注来源口径（官方 / 厂商自报 / 二手 / 存疑）；凡属本项目自身的设计选择，均明确标注为「项目取舍」，不冒充业界共识。
> 本文放在 `docs/`，与技能包 `skill-creator/` 相互隔离；校验结论见 `tests/credibility-report.md`，深度教程见 `skill-creator-guide/`。

## 一、一句话定位

**skill-creator 是一个元技能：把一句模糊需求，变成一个能被另一个模型照着执行的 Skill 包；对已有 Skill，则定位它为什么不被触发、为什么不生效，并给出最小修复。**

「元技能」的意思是：它自己也是一个 Skill，但它生产的不是业务结果，而是别的 Skill。它的输入通常只有一句话——「我每周都要整理这个客户反馈表，能不能让 AI 帮我弄」；它的输出是一个目录、一份 `SKILL.md`、一份自检结论，以及一组需要用户拍板的待确认项。

它不教人成为 Skill 专家。它只做一件事：**在每一步告诉使用者现在该做什么、做到什么程度算过、下一步是什么**。这份节奏感，是它真正要交付的东西。

## 二、调用以后，具体会发生什么

这是最容易被误解的部分。调用 skill-creator 不会立刻得到一份文档，也不会立刻开始写文件。它启动的是一条**带门禁的流水线**：每一步有明确入口、明确出口，不通过就停在原地，不允许带着半成品往下走。

完整的一次调用，时间线如下。

**第 0 步：先判断这件事该不该做成 Skill。** 开场第一句话先声明走哪条线（新建 / 诊断），并列出四项信息是否齐全：用户原话、场景与时机、交付物、边界与反例。随后核对四项判据——复用性（同类任务预期 ≥3 次或团队多人重复）、非显然性（含模型推不出的固定规则 / 口径 / 顺序）、可判定产出（有明确可验收的交付物）、步骤化（≥3 个有序且相互依赖的步骤）。命中 ≥3 项才继续；命中 ≤2 项立即终止，输出「不建议做成 Skill」并逐项说明理由，同时从四类替代方案中选一种给出：一段提示词、一个脚本、一个模板文件、或干脆直接做一次。

这道闸门会让一部分使用者觉得被冒犯，但它拦下的浪费远大于带来的摩擦。一次性问答、纯信息查询、单步格式转换，做成 Skill 不仅浪费制作时间，还占用检索名额、稀释真正有用的 Skill。**敢于劝退，是这个元技能的责任，不是缺陷。**

**第 1 步：把那句话问成一张需求卡。** 访谈分两轮、每轮不超过 3 问，分工固定。第一轮只问与触发有关的事：用户会怎么开口（要原话，不改写、不抽象成术语）、什么任务、谁发起、多久一次。第二轮才问交付与边界：最终交付什么（具体到文件与字段）、明确不做什么、哪些相邻需求别误触发。产出是一张 8 字段需求卡：用户原话 / 真实场景 / 触发时机 / 目标产出 / 关键约束 / 不做什么 / 相邻易混淆需求 / 待确认项。

凡是推断出来的信息，一律标注「推断」，并在交付时一次性请用户确认。**确认之前不写 description。** 用户只给一句模糊需求时不阻塞产出，但推断项必须进交付物末尾的待确认清单。

**第 2 步：写 description，写完立刻验证。** 按三段公式撰写：`做什么（动词 + 对象 + 产出）` + `何时用（触发场景 + 用户原话触发语 + 可识别对象）` + `排除场景`。硬约束是第三人称、单行、≤1024 字符、≥3 条用「」包裹的用户原话触发语、≥1 个可识别对象（文件扩展名、文件名、领域术语），并写清不做的事；禁用「帮助 / 辅助 / 相关 / 各种 / 提升效率 / 智能化 / 一站式」这类空信息词。

写完**立即**用三种说法测试：口语型、术语型、无术语型，各一条，必须来自真实用户原话或高度还原的模拟。3/3 命中才允许进入下一步；任一说法未命中或落在边缘，就停在本步，从需求卡取该类原话补进触发语后重测，不许补正文、不许调阈值。

之所以把验证提前到写完 description 的那一刻，是因为传统做法「全部写完再统一测试」有个致命问题：一旦 description 有问题，前面写正文的时间全白费。**带着「已验证」的状态往下走**，每一步才站得住。

**第 3 步：决定这个 Skill 到底需要几个文件、几个文件夹。** 详见第六节——这是本项目的重心，也是最容易翻车的一步。

**第 4 步：写正文，用固定六段骨架。** 第一动作是复制 `assets/SKILL_TEMPLATE.md`，不凭记忆另起炉灶。六段顺序固定、不可调换、不可缺段：目标 → 前置 → 步骤 → 输出示例 → 禁止项 → 常见错误。每一步写满四要素：输入（具体到文件名 / 字段）、动作（动词开头）、产出（具体到文件名 / 字段）、失败分支（出现 X 时改做 Y），编号 S1…Sn 连续不跳号。

全文把「必要时 / 酌情 / 视情况 / 灵活处理 / 适当」换成可判定的条件句——例如「必要时补充约束方程」要写成「方程数少于未知量数时，补约束方程或运动学关系」；替换不了，说明这一步本身没想清楚，退回去重想。输出示例具体到文件名与必含字段，且每个字段在「目标」或「步骤」里有出处，不写「等等」「示例略」。

**第 5 步：自检与交付。** 按固定顺序跑结构校验（12 项机器检查，0 个 FAIL 才允许交付，WARN 逐条说明保留理由）、触发测试（3/3 命中）、人工语义清单，然后交付四块内容：目录树、`SKILL.md` 全文或路径（附版本号）、自检结论、待确认项。禁止只说「已完成」。结论只有三种：可交付 / 可交付但有待确认项 / 不可交付（并说明退回哪一步）。

**另一条线：诊断模式。** 如果输入是一个已有 Skill 加一句抱怨，就不重跑准入闸门，直接进入诊断。先分类、后动手，未分类不得修改正文：不触发只检查 frontmatter；触发但不生效只动正文与脚本；上下文过载只做外置不删功能；产出不可用只动输出定义。修复后必须重跑第 5 步，并追加一条**由最初导致问题的用户原话**构成的回归用例。

## 三、它到底在解决什么问题

要理解这个元技能，得先理解 Skill 解决的是什么。

模型能力越来越强，但强模型不等于能干活。它不知道你们公司的周报长什么样，不知道这类合同该看哪几条，不知道这个学科的题该怎么一步步解。**Skill 要填的，就是「人知道但模型不知道」这条缝**：把这些隐性知识，固化成模型能照着执行的操作手册。这一点与 Anthropic 官方的比喻一致——官方把构建 Skill 类比为给新员工准备入职指南，把程序性知识打包交付（见 `tests/research/01-concept-origins.md`）。

问题在于，绝大多数想做 Skill 的人，动手时是懵的。他们脑子里有一个模糊念头，然后面对一个空白的 `SKILL.md`，不知道第一行写什么。

以下三类场景是**高度还原的典型场景**，用于说明卡点类型，不作为可核验的真实个案引用：

- **业务专家**：对领域了如指掌，知道一份合格的尽调报告要看哪七个维度，但不懂技术，不知道「描述」和「指令」的区别，容易把 Skill 写成一篇经验总结——读起来很有道理，执行起来没有步骤。卡点是**知识很足，但不知道怎么把它变成可执行的流程**。
- **一线执行者**：被重复劳动困住，清楚自己每天在重复什么，但说不清「这件事的规则是什么」。问他「你怎么判断这个该不该退」，他说「看情况」。卡点是**知道自己烦什么，但提炼不出规则**。
- **半懂技术的人**：看过几篇讲 Skill 的文章，知道有 frontmatter、有渐进式披露、有脚本，于是热衷于把结构做得很「专业」——四个目录、六个文件、一堆脚本，主文件里却全是「请专业地分析」「酌情处理」「根据实际情况调整」。卡点是**形式做对了，内容没落地**。

三类人需要的帮助完全不同，但有一件事共通：**他们都需要被问对问题，然后被按着头走完一条最短的路**。不是给他们一份规范去读，而是有东西在每一步告诉他们「现在该做什么、做到什么算过、下一步是什么」。

现有的三种做法，各自缺了这一环：

1. **给模板**：把六段骨架列出来让你填空。模板解决「长什么样」，解决不了「填什么」。一个新手拿到模板，会在「步骤」那一栏写「分析用户需求，给出专业建议」——因为模板不会告诉他这不算步骤。（此判断属合理推断，有官方 `skill-creator` 走「澄清意图 + 评测迭代」而非填空作为侧面印证，见 `tests/research/02-international-landscape.md`。）
2. **给规范**：详细规定 description 怎么写、主文件不超过多少行、目录怎么组织。规范偏格式与结构，更适合评审，不适合生产；新手读完仍不知道第一句话写什么。（官方《How to create custom skills》与开放规范均属此类；「规范越细越偏离能用」无直接证据，属项目判断。）
3. **给例子**：给几个完整范例让人照着改。例子比前两者好，但它展示的是结果，不是过程。新手看到成品里有 `references/`，就以为自己也该建一个；看到成品一百多行，就以为长度是标准。他不知道那个 `references/` 是因为主文件快超预算才拆出去的。（范例库「展示成品不展示过程」属实；「新手据此误建」未找到直接公开证据，属高度还原的场景推断。）

需要如实说明的是：中文世界在 2026 年已经出现多篇面向新手的体系化教程与多个创建器（详见第七节）。因此**不能说「从来没有人把这些写成给新手看的东西」**。本项目真正补的缺口更窄，也更准确：**已有的多是模板、规范、范例，或绑定特定平台的向导；缺的是一条平台无关、带门禁、把人从一句话按着走到底的最短路径。**

## 四、为什么「教做 Skill」本身要是一个 Skill

因为做 Skill 这件事，符合做成 Skill 的全部条件。

它**高频**：一个人一旦开始做 Skill，通常不会只做一个。它有**稳定流程**：判断该不该做 → 问清需求 → 写 description → 定文件 → 写正文 → 自检，这六步顺序在几乎所有情况下都成立。它有**可判定产出**：一份 `SKILL.md` 加一个目录结构，合不合格有明确标准。它有**依赖关系**：description 没定稿就不能写正文，目录没定就不能写引用。它还需要**专业知识**：什么算可执行的步骤、什么样的 description 能被召回，这些不是模型凭空能推出来的。

更关键的是：做成 Skill 之后，它能把「判断」嵌进流程里。**文档只能陈述标准，Skill 能在每一步真的执行标准**——问用户要原话，拿不到就不往下走；写完 description 立刻测三种说法，不通过就退回重写；主文件超预算就要求拆出去。这种「卡着不让过」的能力，是文档给不了的。

## 五、贯穿全设计的一个判断标准

整份设计围绕一句话展开：

> **另一个模型拿到这个包，能不能不看别处，照着做出同样的结果？**

这个标准朴素，但能筛掉绝大部分不合格的 Skill。「请专业地分析这份合同」不合格，因为另一个模型不知道「专业」指什么；改成「逐条列出违约责任条款，标注触发条件和赔偿上限，缺失的标『未约定』」就合格了。「根据情况调整参数」不合格，因为「情况」没有判定条件；改成「当样本量小于 30 时改用 t 分布，否则用正态近似」就合格了。「参考行业惯例」不合格；「按 GB/T 标准第 X 条」才合格。

（官方最接近的表述是 `self-contained`——自包含；官方 `skill-creator` 也明确写着「这个 skill 是给另一个 Claude 实例用的」。本项目的「可移交性」是对这一概念的操作化，见 `tests/research/04-meta-skill-teaching.md`。）

这个标准解释了两件事。

**第一，为什么 description 比正文更关键。** 正文写得再好，如果 description 无法让 Skill 被召回，它就永远不会被执行——一个从不被调用的 Skill，等于不存在。而在开放标准的渐进式披露机制里，启动时只有 `name` + `description` 常驻在检索上下文（约每技能 100 token 量级），命中后才把 `SKILL.md` 正文读进来，再之后才按需加载 `references/` 与执行 `scripts/`。这是 Anthropic 官方定义并已被 `agentskills.io` 采纳的三层机制（已核实事实，见 `tests/research/01-concept-origins.md`）。**description 的质量直接决定这个 Skill 有没有机会被用上**。所以本项目把它单列一步，要求必须含用户真实原话、必须写清排除场景、必须用三种不同说法验证过。

**第二，为什么「最小起步」要被写死。** 这是下一节的主题。

## 六、S3 目录设计：把「最小起步、按需增量」写死

在整条流水线里，S3 的位置是**紧接 description 之后、正文之前**。它只负责回答一个问题：**这个 Skill 到底需要几个文件、几个文件夹？**

这个位置不是随意排的。description 定稿之前，产出形态还没定，谈目录是空谈；正文开写之后，引用哪些文件必须已经落地，否则会写出悬空路径。所以目录设计必须夹在两者之间，作为一次独立的、有明确产出的决策。

对新手来说，这一步最容易两种翻车：

- **翻车一：建一堆空目录装专业。** 照着别人的成品建 `references/`、`scripts/`、`assets/`，里面全是空的或占位内容。结构看起来很规范，实际没有解决任何问题，反而带来维护成本、加载成本，以及交付时被自己的复杂度绊倒的风险。（该具体现象在公开来源中未逐字命中，属高度还原的典型场景；但官方确有「删除不需要的示例文件」、社区有「勿建无用的 README/CHANGELOG」的对应建议。）
- **翻车二：全塞进 `SKILL.md` 导致上下文过载。** 把能想到的要求全写进去，主文件越来越长，命中后一次性灌进上下文，边界模糊、重点淹没。官方与社区均把超长主文件列为反模式，并给出「主文件控在 500 行内、细节移入 `references/`」的推荐（已核实事实）。

两种翻车看似相反，根子是同一个：**把结构当成目的，而不是手段**。

因此本项目把下面的规则写死，不允许模型自由发挥：

1. **第一动作先输出默认最小集**，只有一个文件：

   ```
   skill-name/
   └── SKILL.md
   ```

   并明确告知使用者：**绝大多数 Skill 一个文件就够；目录是解决问题的手段，不是专业感的装饰**。默认答案永远是「只有一个 SKILL.md」。不得因为「看起来规范」预建任何目录，不预建空目录，不留占位示例文件。

2. **新增任何目录都是例外，例外必须举证。** 按四问顺序逐项判断，答「是」才加，答「否」就不加；每加一个目录，必须用一句话回答「为什么这段内容不能放主文件」，答不出来就不加：

   | 顺序 | 判断问题 | 答「是」→ 加 | 判断标准 |
   | --- | --- | --- | --- |
   | ① | 是否有大量细节需要「用到才读」，放进主文件会挤占上下文？ | `references/` | 单段内容超过主文件预算的 15%，或只在某一步需要 |
   | ② | 是否有确定性操作，每次让模型现场发挥会不一致？ | `scripts/` | 同一段逻辑要重复写，或结果必须可复现 |
   | ③ | 产出中是否有需要被复制、填充的模板文件？ | `assets/` | 它是给产出物用的，不是给模型读的 |
   | ④ | 是否需要供人阅读的完整成品范例？ | `examples/` | 范例是教学用途，不是运行时依赖 |

   第 5 类不参与四问、也不进技能包：测试数据、说法清单、测试报告、回归用例一律放与技能包平级的独立 `tests/`。

3. **输出格式固定三块**：目录树 → 每个目录一行理由（模板：`<路径> → 不能放主文件的原因 + 加载/执行时机`）→ 主文件行数预算（目标 ≤300 行，绝对上限 500 行）。

4. **自检五项全过才进入 S4**：是否从最小集起步 / 每个新增目录是否都有一句话理由 / 树中每个路径是否都会真实创建 / 行数预算是否给出 / 测试资产是否已排除包外。

5. **失败分支也不许绕过最小集**：使用者坚持建多个目录却给不出理由 → 先按最小集产出，把想要的目录列入待确认项，说明维护与加载成本，请用户拍板，不擅自扩目录；使用者要求全塞一个文件且明显超 500 行 → 指出超限风险并给拆分建议，仍由用户决定。

一句话概括 S3 的设计意图：**先给最少的，再为每一个新增项索取理由**。这样「建一堆空目录」和「全塞一个文件」两种翻车，都被同一条规则挡住——前者因为没有理由而建不起来，后者因为超预算而必须外置。

## 七、功能清单

按能力域列出当前实现的功能（对应 `skill-creator/SKILL.md` v1.4.0 的真实内容）：

**A. 准入与澄清**
- A1 走线声明：开场说明新建线 / 诊断线，以及四项信息齐全度。
- A2 准入闸门：四项判据、≥3 才继续、≤2 立即终止并给四类替代方案。
- A3 两轮访谈：触发相关 / 交付与边界，分工固定，每轮 ≤3 问。
- A4 需求卡：8 字段，推断项标注「推断」，确认前不写 description。

**B. 触发面**
- B1 description 三段公式与硬约束（人称、长度、≥3 条「」原话、可识别对象、排除场景、空信息词黑名单）。
- B2 三种说法触发测试：口语 / 术语 / 无术语各一条，固定阈值（命中 ≥0.30 / 边缘 ≥0.18 / 显式触发语加成 +0.35），3/3 门禁，未达标停留 S2。
- B3 触发语词库与正反例、平台字段说明（`references/description-writing.md`）。

**C. 结构**
- C1 默认最小集 + 四问增量决策表 + 固定输出格式 + 自检五项（`references/directory-design.md`）。
- C2 行数预算与渐进式披露三层说明。
- C3 测试隔离：说法清单、报告、回归用例一律放平级 `tests/`，由校验项 P011 做机制性保障。
- C4 引用完整性：主文件引用的每个路径必须真实存在（P006）。

**D. 正文**
- D1 六段骨架模板（`assets/SKILL_TEMPLATE.md`）与逐段标准、四要素写法、模糊词→条件句替换表（`references/body-skeleton.md`）。
- D2 输出示例具体到文件名与字段、每个字段有出处。
- D3 占位符清零（`{{...}}` / `TODO` / `待补充`，P007）。

**E. 校验与交付**
- E1 `validate_skill.py`：12 项结构检查 P001–P012，覆盖 frontmatter、name、description、人称、触发语、引用路径、占位符、行数、空泛词、排除场景、目录规范、资源索引；仅标准库；FAIL 退出码 1，WARN 不影响退出码但须逐条说明。
- E2 `check_triggers.py`：字符二元组重合度 + 显式触发语加成的代理测试，3/3 判定。
- E3 12 项人工语义清单，逐项三态（通过 / 待确认 / 不通过）+ 理由（`references/self-check.md`）。
- E4 交付四块：目录树、主文件路径与版本号、自检结论、待确认项；三种结论判定。
- E5 证据留存：两份报告只追加不覆写，新版本另起一节，历史节保留；失败拦截单列根因与修法；当日日志追加。

**F. 诊断**
- F1 四类症状决策树（不触发 / 不生效 / 上下文过载 / 产出不可用），先分类后动手。
- F2 每类症状的「仅先检查」与「不做什么」边界，最小修复清单。
- F3 修复后重跑 S5 并追加由最初问题原话构成的回归用例。

**G. 配套资产**
- G1 三份完整范例：经典力学求解器（含量纲校验脚本与真实数值结果）、线性代数证明核验、不触发诊断实录。
- G2 7 份 `references/`（571 行）、1 份模板、2 个校验脚本（419 行）。

## 八、设计上的取舍（明确标注哪些是项目选择）

以下六条中，前三条有外部依据，后三条属于**本项目自身的设计取舍，不是业界共识**，此处如实标明。

**取舍一：先判断该不该做，再谈怎么做。** 依据：官方对「好 Skill」的标准是「具体、可重复、聚焦单一工作流」（部分相符）。很多 Skill 的失败不是做得不好，是根本不该做。

**取舍二：description 写完立刻验证，不通过不往下走。** 依据：官方 `skill-creator` 有 description improver 与触发查询迭代（相符）；但「门禁式卡住」的具体形态是本项目做法，官方走的是评测迭代闭环。

**取舍三：每一步必须写清失败分支。** 一个步骤如果写不出失败分支，说明它没有可判定的成功标准——要么太模糊，要么根本不需要存在。强迫填写这一栏，本质上是强迫作者想清楚「什么情况算做完、什么情况要回头」。（此条为项目做法，官方只给出「祈使式、具体」的方向性建议，未找到对应表述。）

**取舍四：自检只留少量、不做长篇清单。** 背景描述主张「清单越长越容易被跳过，五条足矣」。**这是项目取舍，未找到外部依据，且与当前实现不一致**：现有 `references/self-check.md` 是 12 项人工清单，脚本另有 P001–P012 共 12 项机器检查，此外还有 S3 自检五项、S4 自检六项、S5 元自检六问。这是背景蓝图与已实现版本之间的口径差，尚未收敛。

**取舍五：不在元技能里内置测试框架。** 背景描述主张「不需要单独的测试框架、分层测试体系、代理指标，它们会自我繁殖成比被测对象更复杂的系统」。**必须说明：这与业界领先实例不相符**——Anthropic 官方 `skill-creator` 当前版自带 `agents/grader.md`、`agents/comparator.md`、`agents/analyzer.md`、`eval-viewer/generate_review.py` 与独立 description improver，是完整的评测体系，体量可超过被制作的 Skill。本项目选择轻量路线是一条**可以坚持但必须诚实标注的差异化取舍**，不能说成「业界都认为不该做」。

更要如实交代的是：本项目自己也已建立 `validate_skill.py`（255 行、12 项检查）、`check_triggers.py`（164 行、代理指标）、两份实测报告与三个诊断夹具。严格说，并未完全践行「不建测试框架」。背景里那句「工具的复杂度应该低于它服务的对象」，当前只做到一半。

**取舍六：元技能只管「做一个 Skill」，不管组织级治理。** 灰度发布、权限收敛、线上观测、退役归档属于把 Skill 当产品运营的范畴。依据：官方 `skill-creator` 范围仅创建 / 修改 / 打包，Coze 的治理在平台层而非创建器（相符）。一开始就塞进企业级发布审批与安全审查，新手会被吓退，而且他只是给自己做一个周报工具时，那些步骤完全不适用。

## 九、与国内外现状的关系

**标准层面（已核实事实）**：Agent Skills 由 Anthropic 于 2025-10-16 在 Claude Code 首发，2025-12-18 发布为开放标准，2026-10-22 捐赠给 Linux Foundation 旗下 AAIF 中立治理，`agentskills.io` 为官方规范站。因此本文所说的 Skill，指的是这一开放格式，不是某厂商的专有功能。

**国外生态（多口径）**：Anthropic 在捐赠公告中称已有 70+ 平台集成、累计发布约 100 万个技能、安装近 2.8 亿次——**这是厂商自报口径，未经独立审计**。可独立查证的是 Cursor、VS Code / GitHub Copilot、Gemini CLI、OpenAI Codex 均有官方层面的 Skill 支持文档。技能目录站数量彼此矛盾（7 万 / 14.6 万 / 66.5 万 / 70 万），一律不作为事实引用。学术侧 2026 年已有 SkillsBench、SkillRet（16,129 个公开技能的检索基准）、「Is Progressive Disclosure All You Need?」（REALM@ACL 2026）等研究；其中「渐进式披露买的是上下文，不是智能」以及「同能力族误检索：Recall@3 达 0.91 但 HSR@3 仅 0.39」两项，既支持本项目对 description 的重视，也提示**触发过宽同样有害**，排除场景不可省。

**国内生态（需区分口径）**：明确兼容开放格式的是腾讯 CodeBuddy / WorkBuddy、智谱、MiniMax、Kimi；扣子、阿里通义灵码 / Qoder、百度文心快码属自有智能体 / 插件体系，不可混称「兼容 Agent Skills」。中文社区已出现体系化教程，共识性说法是「description 是写给 AI 的触发器，不是写给人的总结」。技能商店确实存在，但「总规模」缺乏权威统计。

**本项目的差异化定位**：官方 `skill-creator` 走的是**评测驱动的迭代优化**路线（写测试提示 → 跑 A/B 对照 → 定量评估 → 优化 description → 循环至满意）；本项目走的是**门禁驱动的最短路径**路线（准入 → 澄清 → 描述 → 目录 → 骨架 → 自检），并把「最小起步、按需增量」写死在 S3。两条路线服务的使用者不同：前者面向要反复打磨、量化优化的熟练作者，后者面向只有一句话、不知道从哪下手的新手。这个差异是真实的，也是本项目值得存在的原因。

## 十、边界：什么不做

一个负责任的 Skill 必须写清自己不做什么，否则会在不该出手的时候出手。

- **不覆盖具体平台的界面操作与账号授权。** 这些是操作指南，不是可复用的方法，各平台差异大、很快过期。
- **不覆盖复杂工程集成。** CI/CD、外部服务鉴权、大型代码库改造需要的是工程能力，不是 Skill 能封装的。
- **不替用户做业务决策。** 能告诉用户「你的 description 缺触发语」，不能替他决定「这个 Skill 该不该上线」。判断标准可以给，拍板必须是人。
- **不为交付而硬做。** 闸门判断不该做，就明确说不建议做并给替代方案。
- **不把测试资产放进技能包。** 技能包应平台无关；测试结果强依赖具体模型与平台，塞进包里等于把开发环境一起交付。

## 十一、怎么算成功

**不看它自己有多少行、有几个文件、跑过多少次校验。** 看的是：一个从来没做过 Skill 的人，用它走完一遍，产出的东西能不能被另一个模型直接执行。

成功的样子：用户给一句「我每周都要整理这个客户反馈表」，经过提问拿到需求卡，确认后得到一份 description，里面写着「当用户说「整理这周的客户反馈」「把这个表归类一下」「客户反馈汇总」时使用」，还写着「不覆盖退款金额核算」；然后是一份六段正文，每一步都能看出输入是什么、做什么、产出什么、什么情况要回头；最后自检通过。这个人可能只花了半小时，但做出来的东西，比自己闷头写三天要能用得多。

失败的样子同样清楚：产出的 Skill 结构很漂亮，但 description 里没有一句用户会说的话；或者步骤写得很详细，全是「酌情」「视情况」；或者自检报告写着「全部通过」，真正拿去测三种说法一种都没触发。

## 十三、结语

做 Skill 这件事，本质上是把隐性知识显性化：一个人脑子里的经验，要变成另一个模型能执行的动作序列，中间隔着的不是技术，是表达——把「我知道该怎么做」翻译成「任何人照着做都能做对」。

这个翻译过程有方法，方法也不难；难的是在每一步都知道自己该做什么、做到什么程度算够、什么情况下该退回去。**新手缺的不是知识，是节奏感。**

skill-creator 提供的就是这样一种节奏：一道闸门判断该不该做，两轮提问问清需求，一个公式写出 description 并立刻验证，一张决策表决定要不要加目录（默认永远只有一个 `SKILL.md`），六段骨架保证正文完整，最后用自检守住底线。每一步都有明确的入口和出口，每一步都不需要用户自己去想「接下来呢」。

它不追求让使用者成为 Skill 专家，只追求让他走完这一遍之后，手上有一个真能用的东西。而这，大概就是一个教人做事的工具，能给出的最好的东西。
