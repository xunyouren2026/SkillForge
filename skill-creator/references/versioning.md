# 版本与变更日志（A1）专业规范

## 1. 引言：版本与变更日志的定位

### 1.1 问题的提出

Skill 交付后还要改：description 补触发语、正文加步骤、references 拆文件。每次改动都要能回答三件事：改了哪个文件、哪版改的、旧版还能不能用。如果这三件事没有固定落点，维护就会退化成“凭记忆改、凭感觉交付”：改了什么说不清，哪版改的查不到，旧版还能不能用无法判断。版本与变更日志（A1）的目的，就是给这三件事一个固定落点。

A1 不是“写个版本号”这么简单。版本号是改动类型的编码，CHANGELOG 是改动根因与影响面的记录，回归用例是改动有效性的证据。三者缺一，版本管理就不完整。

### 1.2 与 A2、A3、A4 的关系

A2 是交付前的平台适配检查，A3 是交付后的周期性健康度体检，A4 是交付后的增量更新流程，A1 是贯穿始终的版本与变更记录。四者的关系：

- **A1 在建包时建立基线**：首次交付时写入 `1.0.0` 和第一条 CHANGELOG。
- **A2 在交付前检查字段**：A2 的核对结果写入 A1 的 CHANGELOG。
- **A3 在运行时体检**：A3 的体检报告按版本归档，A1 记录版本变化。
- **A4 在改动时更新**：A4 的每次改动都触发 A1 的版本升位与 CHANGELOG 追加。

A1 是其他三本手册的“记录层”。没有 A1，A2 的核对结果无处归档，A3 的体检报告无法按版本追溯，A4 的改动无法判断影响面。

### 1.3 核心原则

A1 的四条原则：

1. **每次改动都有版本**：改一个字也算版本变动，version 字段同步 +1。
2. **每次版本都有记录**：CHANGELOG 只追加不覆写，四栏齐全。
3. **每次记录都有证据**：回归用例取自最初问题原话，不是新编说法。
4. **每次交付都可追溯**：旧版测试记录保留，凭版本号判断旧记录是否还算数。

## 2. 版本号规则详解

### 2.1 语义化版本三段

版本号用语义化三段：`主版本.次版本.修订号`。三段分别对应三类改动：

- **主版本**：触发面变化。description 增删触发语、排除场景变化、触发条件变化。
- **次版本**：产出形态变化。正文步骤增删、references 结构调整、输出示例变化。
- **修订号**：不影响触发面与产出形态的修正。错别字、路径大小写修正、格式调整。

三段之间是“就高原则”：一次改动如果同时涉及触发面和正文，按主版本 +1，不按次版本 +1。

### 2.2 改动类型与版本位对应表

| 改动类型 | 版本位 | 例子 | 判定依据 |
| --- | --- | --- | --- |
| description 增删触发语 | 主版本 +1 | 1.0.0 → 2.0.0 | 触发面变化 |
| description 增删排除场景 | 主版本 +1 | 2.0.0 → 3.0.0 | 触发面变化 |
| description 改人称、改措辞但不改触发面 | 修订号 +1 | 3.0.0 → 3.0.1 | 触发面未变 |
| 正文步骤增删 | 次版本 +1 | 3.0.1 → 3.1.0 | 产出形态变化 |
| references 拆分或合并 | 次版本 +1 | 3.1.0 → 3.2.0 | 产出形态变化 |
| 输出示例补字段 | 次版本 +1 | 3.2.0 → 3.3.0 | 产出形态变化 |
| 错别字修正 | 修订号 +1 | 3.3.0 → 3.3.1 | 不影响触发面与产出 |
| 路径大小写修正 | 修订号 +1 | 3.3.1 → 3.3.2 | 不影响触发面与产出 |

### 2.3 就高原则的适用情形

就高原则用于“一次改动涉及多类”的情形。具体规则：

1. 触发面 + 正文 → 主版本 +1。
2. 触发面 + 修订 → 主版本 +1。
3. 正文 + 修订 → 次版本 +1。
4. 触发面 + 正文 + 修订 → 主版本 +1。

就高原则的理由：触发面变化的影响面最大，下游需要重新跑触发测试；正文变化的影响面次之，下游需要重新跑产出测试；修订的影响面最小，下游可以只做抽查。

### 2.4 不确定归类的判定流程

不确定归哪类时，按以下流程判定：

**第一步：问触发面是否变化。** 如果 description 的触发语、排除场景、触发条件有任何变化，归主版本。

**第二步：问产出形态是否变化。** 如果正文步骤增删、references 结构调整、输出示例变化，归次版本。

**第三步：问是否只是文字修正。** 如果只是错别字、格式、路径大小写，归修订号。

**第四步：如果三步都说不清，按就高原则。** 触发面动过就算主版本；没动过但正文动过就算次版本；都没动过就算修订号。

### 2.5 常见版本号错误

| 错误 | 症状 | 修复 |
| --- | --- | --- |
| 触发面变了但只升修订号 | 下游以为触发面未变，不重跑触发测试 | 改为升主版本，补 CHANGELOG |
| 正文步骤增删但只升修订号 | 下游以为产出形态未变，不重跑产出测试 | 改为升次版本，补 CHANGELOG |
| 版本号跳错（1.0.0 直接到 3.0.0） | 中间缺了版本记录，追溯断裂 | 回看 CHANGELOG 缺了哪次触发面改动，补记或说明合并原因 |
| 版本号不升位就交付 | 下游无法判断当前版本是否包含修复 | 回 A1 第 2 节，升位并写 CHANGELOG |
| 版本号格式不统一（1.0 / v1.0.0） | 追溯时无法按版本号排序 | 统一为三段式，不带 `v` 前缀 |

## 3. CHANGELOG.md 规范

### 3.1 位置与只追加原则

每个技能包根目录放一份 `CHANGELOG.md`。只追加不覆写，新版本另起一节，旧版本条目保留。

只追加的理由：CHANGELOG 是追溯的依据。覆写会丢失历史，导致“旧版还能不能用”无法判断。

### 3.2 四栏模板详解

CHANGELOG 每条固定四栏：

```
## [版本号] 日期
### 改了什么
### 改动原因
### 影响面
### 回归用例
```

四栏缺一不可。缺“改了什么”，追溯时不知道改了什么；缺“改动原因”，下一次改动无法判断是否重复；缺“影响面”，联动检查无法做；缺“回归用例”，改动有效性无法验证。

### 3.3 “改了什么”的写法要求

“改了什么”要逐字记录，不能概括。具体要求：

1. 写清改了哪个文件、哪一段、改前是什么、改后是什么。
2. 涉及多个文件时，逐文件列出。
3. 涉及删除时，写清删除了什么、删除原因。
4. 涉及新增时，写清新增了什么、新增位置。

示例：

> - `SKILL.md` 的 description 字段：原为“处理线性常微分方程”，改为“处理一阶线性常微分方程，包括积分因子法、常数变易法”。
> - `SKILL.md` 的 S4 步骤：补失败分支“若方程不是一阶线性，回 S2 重新判定”。

不能写“优化了 description”“补了失败分支”这种概括性描述。

### 3.4 “改动原因”的写法要求

“改动原因”要写根因，不能写“用户要求”。根因要具体到触发条件或失败现象。

示例：

> - 术语型说法连续两轮未命中：用户说“这个一阶线性 ode 用积分因子怎么列式”时未触发。
> - S4 步骤缺失败分支，导致非一阶线性方程被误处理。

不能写“为了更好用”“用户反馈有问题”这种模糊理由。

### 3.5 “影响面”的写法要求

“影响面”要写联动分析，不能写“无影响”。联动分析包括：

1. 触发面是否变化，是否需要重跑三种说法测试。
2. 正文步骤编号是否变化，下游引用是否受影响。
3. references 路径是否变化，加载指令是否需要更新。
4. 待确认项是否变化。

示例：

> - 触发面变宽，需重跑三种说法测试。
> - 正文步骤编号未变，下游引用不受影响。
> - 未新增 references，加载指令不变。

### 3.6 “回归用例”的写法要求

“回归用例”要写原话，不能写新编说法。原话要逐字记录，并写清预期结果。

示例：

> - 「这个一阶线性 ode 用积分因子怎么列式」→ 应命中。
> - 「二阶非线性方程怎么解」→ 应排除。

### 3.7 版本条目格式与日期

版本条目格式：

```
## [2.0.0] 2026-11-14
```

日期用 ISO 格式 `YYYY-MM-DD`，不用“11月14日”这种模糊写法。版本号用方括号包裹，便于检索。

### 3.8 合并与拆分条目的规则

**合并**：如果同一天有多次改动，合并为一条，版本号取最高位。合并时逐项列出改动，不省略。

**拆分**：如果一次改动涉及多个不相关主题，拆分为多条，每条独立版本号。拆分的理由是：不相关主题的版本号混在一起，追溯时无法按主题查找。

## 4. 回归用例管理

### 4.1 回归用例的定义与来源

回归用例是“最初导致问题的用户原话”，不是新编的说法。定义包含三个要素：

1. **原话**：用户实际说出的那句话，逐字记录。
2. **来源**：这句话来自哪个需求卡、哪次会话、哪个报告。
3. **预期结果**：这句话应该触发还是应该排除。

新编说法只能作为补充用例，不能替代原话。新编说法可能偏离真实场景，用新编说法做回归，可能测出“假通过”。

### 4.2 资产存放位置

| 资产 | 位置 | 理由 |
| --- | --- | --- |
| 说法清单 | 技能包外 `tests/phrasings-*.txt` | 数据不进包，避免包体积膨胀 |
| 回归用例 | 技能包外 `tests/fixtures/` 或报告附录 | 用例是运行时资产，不是 Skill 组成部分 |
| 历史报告 | `tests/trigger-test-report.md`，只追加不覆写 | 报告按版本归档，便于趋势对比 |
| 方法文档 | 包内 `references/trigger-test.md` | 方法是 Skill 的一部分 |
| 工具脚本 | 包内 `scripts/check_triggers.py` | 工具是 Skill 的一部分 |

### 4.3 包内与包外分离原则

包内只留方法文档与工具，不留数据。分离原则的理由：

1. **包体积**：数据会随版本累积，导致包体积膨胀。
2. **可移植性**：数据与平台相关，包需要跨平台移植。
3. **可追溯性**：数据放包外，按版本归档，追溯时不受包版本限制。

### 4.4 用例格式与命名

用例格式：

```
用例编号 | 来源（原话/新编） | 原话文本 | 预期结果 | 实际结果 | 通过/失败
```

命名规则：

- 说法清单：`phrasings-v<version>.txt`。
- 回归用例：`fixtures/<version>/<case-id>.json`。
- 历史报告：`trigger-test-report.md`，按版本分节。

### 4.5 用例生命周期

用例生命周期：

1. **新增**：每次发现新触发失败，追加原话到说法清单。
2. **回归**：每次 description 改动，重跑全部用例。
3. **废弃**：用例不再适用时，标“已废弃”并写清废弃原因，不直接删除。
4. **归档**：版本升级后，旧用例归档到 `fixtures/<old-version>/`，保留可追溯。

### 4.6 历史报告管理

历史报告只追加不覆写，新版本另起一节。每节记录：版本号、测试日期、测试用例数、通过数、失败数、失败用例根因。

历史报告的作用是趋势对比：连续多次失败说明有系统性问题，单次失败可能只是偶发。

## 5. 改 description 的硬规矩

### 5.1 逐字变动与版本同步

改一个字也算版本变动，version 字段同步 +1。具体要求：

1. 改动前记录 description 原文。
2. 改动后记录 description 新文。
3. version 字段同步升位。
4. CHANGELOG 记录改前改后。

不能写“改了几个字，不算版本变动”。触发面是逐字匹配的，改一个字可能改变触发行为。

### 5.2 三种说法整体重跑

改完三种说法整体重跑，不许只测改动涉及的那一条。三种说法指：

1. **原话**：最初导致问题的用户原话。
2. **近义改写**：原话的近义说法，验证触发面是否过窄。
3. **反面场景**：应该被排除的说法，验证排除面是否过宽。

只测一条的风险：改动可能修复了原话，但破坏了近义改写或反面场景。整体重跑才能发现联动问题。

### 5.3 旧版测试记录保留

旧版测试记录保留，标清版本号与重测原因。凭版本号判断旧记录是否还算数。

保留规则：

1. 旧版记录不删除，标“已废弃”或“已归档”。
2. 重测原因写清：重测触发条件、重测结果与旧版差异。
3. 版本号是判断依据：旧版记录只对旧版有效，新版必须重新测试。

### 5.4 主版本与次版本判定

改 description 时，版本位判定：

1. 触发面变化（增删触发语、排除场景、触发条件）→ 主版本 +1。
2. 触发面未变（改人称、改措辞但不改触发语）→ 修订号 +1。
3. 正文同时改动 → 按就高原则，主版本 +1。

### 5.5 改 description 的操作流程

**第一步：锁定正文。** 用 diff 工具确认正文逐字不变。

**第二步：记录改前改后。** description 原文与新文逐字记录。

**第三步：升位。** 按 5.4 判定版本位，version 字段升位。

**第四步：重跑三种说法。** 原话、近义改写、反面场景全部重跑。

**第五步：写 CHANGELOG。** 四栏齐全，回归用例写原话。

**第六步：归档旧记录。** 旧版测试记录标版本号，新版另起一节。

## 6. 正文改动与 references 结构调整的版本处理

### 6.1 正文步骤增删

正文步骤增删属于次版本 +1。具体要求：

1. 记录增删的步骤编号。
2. 检查步骤编号是否连续。
3. 检查下游引用是否受影响。
4. CHANGELOG 写清增删内容与影响面。

### 6.2 references 拆分与合并

references 拆分或合并属于次版本 +1。具体要求：

1. 记录拆分或合并的文件路径。
2. 检查主文件加载指令是否更新。
3. 检查加载时机是否写清。
4. CHANGELOG 写清拆分或合并理由与影响面。

### 6.3 联动检查

正文改动与 references 调整后，必须做联动检查：

1. 步骤编号是否连续。
2. references 路径是否存在。
3. 加载指令是否指向正确文件。
4. 待确认项是否变化。

联动检查有一项不过，回对应步骤修，不许带病交付。

### 6.4 版本位选择

正文步骤增删 → 次版本 +1。references 结构调整 → 次版本 +1。正文与 references 同时改动 → 次版本 +1。正文改动同时涉及触发面 → 主版本 +1。

## 7. 失败分支与处置

### 7.1 四类失败情形

| 情形 | 处置 |
| --- | --- |
| 忘了记 CHANGELOG 就交付 | 交付四块里补「本次变更」一行，再交付 |
| 旧版测试记录找不到了 | 标「历史记录缺失」，用当前版本重跑三种说法，不拿旧记录充数 |
| 版本号跳错（1.0.0 直接到 3.0.0） | 回看 CHANGELOG 中间缺了哪次触发面改动，补记或说明合并原因 |
| 回归用例不命中 | 回 A1 第 4 节，从需求卡补该类原话，重跑三种说法 |

### 7.2 处置流程

**忘了记 CHANGELOG**：交付前补记，不能“下次补”。补记时写清改了什么、改动原因、影响面、回归用例。

**旧版测试记录找不到**：标“历史记录缺失”，用当前版本重跑三种说法。不能拿旧记录充数，旧记录可能对应不同版本，用它做回归会得出错误结论。

**版本号跳错**：回看 CHANGELOG，找中间缺了哪次触发面改动。如果是合并，说明合并原因；如果是漏记，补记。

**回归用例不命中**：从需求卡补该类原话，重跑三种说法。不能自己编新说法，新说法可能偏离真实场景。

### 7.3 升级路径

如果失败分支处置后仍无法追溯，升级到完整流程。A1 只处理版本与变更记录，不处理结构性缺陷。结构性缺陷必须回到 S1–S30 完整流程。

## 8. 输出前自检与交付标准

### 8.1 自检清单

- [ ] version 字段与 CHANGELOG 最新条目一致？
- [ ] 每次 description 改动都有三种说法整体重跑记录？
- [ ] 回归用例取自最初问题原话，不是新编？
- [ ] 旧版记录保留且标清版本号？

### 8.2 自检执行方式

自检要逐项确认，不能凭印象打勾。每一项都要有证据：

1. version 一致性：对照 version 字段与 CHANGELOG 最新条目的版本号。
2. 三种说法记录：查 `tests/trigger-test-report.md` 最新一节，确认三种说法都有记录。
3. 回归用例原话：查 CHANGELOG 的回归用例栏，确认标注“原话”来源。
4. 旧版记录：查 `tests/fixtures/` 目录，确认旧版用例已归档。

### 8.3 交付标准

四项自检全过才能交付。任一项不过，回 A1 第 3、4 节补齐，不进入交付。交付时附带：CHANGELOG 最新条目、三种说法测试记录、回归用例清单、版本号对照表。

## 9. 与 A2、A3、A4 的衔接

### 9.1 A2 结果的 A1 记录

A2 的平台适配核对结果，写入 A1 的 CHANGELOG。记录内容：目标平台、已核对字段、待确认字段、存疑字段。

### 9.2 A3 体检的 A1 归档

A3 的体检报告按版本归档。A1 记录版本变化，A3 报告记录该版本的健康度。追溯时按版本号关联 A1 与 A3。

### 9.3 A4 改动的 A1 更新

A4 的每次改动触发 A1 的版本升位与 CHANGELOG 追加。A4-1 改 description → 主版本或修订号；A4-2 改正文 → 次版本；A4-3 加 reference → 次版本。

## 10. 工具与自动化可选实现

### 10.1 版本号校验脚本

写一个 `scripts/check_version.py`，检查：

1. version 字段格式是否合法（三段式）。
2. version 字段与 CHANGELOG 最新条目是否一致。
3. CHANGELOG 条目是否四栏齐全。

### 10.2 CHANGELOG 模板生成

写一个 `scripts/new_changelog.py`，输入版本号、改动类型、改动内容，自动生成 CHANGELOG 条目骨架。

### 10.3 回归用例管理脚本

写一个 `scripts/manage_fixtures.py`，管理回归用例的新增、归档、废弃。

### 10.4 自动化边界

自动化只能做格式校验与模板生成，不能替代人工判断。改动类型判定、根因分析、影响面分析，仍需人工完成。

## 11. 常见错误与风险分析

### 11.1 常见错误

| 错误 | 风险 | 预防 |
| --- | --- | --- |
| 版本号不升位 | 下游无法判断是否包含修复 | 交付前自检 version 一致性 |
| CHANGELOG 只写“修了 bug” | 追溯时不知道改了什么 | 四栏齐全，逐字记录 |
| 回归用例用新编说法 | 测出“假通过” | 回归用例取自原话 |
| 旧记录删除 | 追溯断裂 | 只追加不覆写，旧记录归档 |
| 版本号跳错 | 中间改动丢失 | 回看 CHANGELOG，补记或说明合并原因 |

### 11.2 风险分析

**追溯断裂**：没有 CHANGELOG 或 CHANGELOG 不完整，导致无法判断旧版是否还能用。后果是下游可能继续使用有缺陷的旧版。

**触发面误判**：版本号未按触发面变化升位，导致下游不重跑触发测试。后果是触发面缺陷带进交付。

**回归失效**：回归用例用新编说法，导致测试通过但真实场景仍失败。后果是“假通过”掩盖真实缺陷。

## 12. 总结

A1 手册的核心是四句话：**每次改动都有版本，每次版本都有记录，每次记录都有证据，每次交付都可追溯。**

版本号是改动类型的编码：主版本对应触发面，次版本对应产出形态，修订号对应文字修正。就高原则用于多类改动同时发生的情形。

CHANGELOG 是改动根因与影响面的记录：四栏齐全，逐字记录，只追加不覆写。

回归用例是改动有效性的证据：取自最初问题原话，不编新说法；包外存放，按版本归档。

A1 与 A2、A3、A4 形成闭环：A2 建包时记录平台适配，A3 运行时记录健康度，A4 改动时记录增量更新。四本手册各司其职，版本管理才能从“凭记忆”变成“可追溯”。
