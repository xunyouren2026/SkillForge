# 增量更新流程（A4）专业规范

## 1. 引言与适用范围

### 1.1 背景

Skill 交付之后，维护阶段面临的典型问题是：改动往往很小，但影响面未必小。全量重跑 S1–S30 能保证不漏，代价是时间与算力；局部改动能省时间，但如果漏掉联动步骤，就会把缺陷带进交付。A4 手册的目的，是在“全量重跑”与“局部改”之间给出第三条路径：**按改动类型走最小路径，但最小路径的终点必须是整体重跑，不是局部重跑。**

### 1.2 适用对象

本手册适用于 Skill 已通过 S1–S30 首次交付之后的增量维护。首次交付不适用 A4，必须走完整流程。增量维护包括三类改动：只改 description、只改正文某步、只加 reference。三类之外的改动（如新增步骤、删除步骤、修改能力边界）不属于 A4 范围，必须回到完整流程。

### 1.3 核心原则

A4 的四条原则：

1. **最小路径**：三类改动各配一条路径，只跑该跑的步骤，不重复全量。
2. **联动检查**：任何改动后必须回答三问（路径存在、编号连续、待确认项不变），有一问不过就不交付。
3. **回归验证**：回归用例取自最初导致问题的那句用户原话，不是新编说法。
4. **整体重跑**：路径可以最小，但验证必须整体。禁止只测改动涉及的那一条说法。

## 2. 改动分类与判定

### 2.1 三类改动

**A4-1 只改 description**：frontmatter 的 description 字段变化，正文逐字不变。典型场景：补触发语、改排除场景、修人称。

**A4-2 只改正文某步**：正文中某一步的写法变化，步骤编号与整体结构不变。典型场景：步骤缺失败分支、模糊词换条件句、输出示例补字段。

**A4-3 只加 reference**：主文件超预算，把某段细节外置为 references/ 下的独立文件。典型场景：主文件接近长度上限，某段细节只服务少数场景。

### 2.2 判定流程

判定顺序：先看 frontmatter 是否变化。description 变、正文不变 → A4-1。再看正文步骤编号是否变化。编号不变、某步内容变 → A4-2。再看是否新增文件。主文件缩短、references/ 新增文件 → A4-3。三类都不是 → 回到完整流程。

判定错误是 A4 最常见的失败源。把“改正文”误判为“改 description”，会导致回归用例选错、联动检查漏做。判定时必须逐字比对，不能凭印象。

### 2.3 变更影响分析表

## 3. A4-1：仅修改 description

### 3.1 适用场景

description 是 Skill 的触发面，决定 Skill 在什么场景下被加载。A4-1 只处理触发面的变化，不处理产出形态的变化。补触发语、改排除场景、修人称，都属于 A4-1。顺手改正文、顺手加功能、顺手扩能力边界，都不属于 A4-1。

### 3.2 操作步骤

**第一步：只动 frontmatter 的 description 字段，正文逐字不变。** 操作时先把正文用 diff 工具锁定，确认改动前后正文完全一致。description 的改动要写清改前改后，不能只写“优化了描述”。

**第二步：version 按语义化规则升位。** description 变化属于触发面变化，不改变 Skill 的产出能力，按次版本 +1 处理。version 升位必须与 CHANGELOG 一致，不能只升 version 不写记录。

**第三步：用最初问题原话做回归用例，重跑三种说法测试。** 回归用例必须取自最初导致问题的那句用户原话。三种说法指：原话、原话的近义改写、原话的反面场景（应该被排除的说法）。三种说法都跑，不能只跑原话。

**第四步：记录 before / after 与重测结果到 CHANGELOG。** 记录格式：改前 description 原文、改后 description 原文、三种说法的测试结果（命中/未命中）、version 变化。

### 3.3 回归用例设计

A4-1 的回归用例必须针对触发面。如果最初问题是“Skill 在该触发时没触发”，回归用例就是那句没触发的原话。如果最初问题是“Skill 在不该触发时触发了”，回归用例就是那句误触发的原话。不能拿产出形态的原话做 A4-1 的回归用例，那是 A4-2 的事。

三种说法的设计：原话验证修复是否生效；近义改写验证触发面是否过窄；反面场景验证排除面是否过宽。三者缺一，触发面的回归就不完整。

### 3.4 禁止事项与理由

禁止顺手改正文：A4-1 的验证只覆盖触发面，不覆盖产出形态。改正文会让产出形态变化，但 A4-1 的回归用例测不出来。

禁止顺手加功能：加功能属于能力边界变化，不属于 A4 范围。

禁止顺手扩能力边界：扩边界会改变 Skill 的适用范围，必须回到完整流程。

### 3.5 常见错误

最常见错误是把“改正文某步的措辞”误判为 A4-1。判定标准是：正文是否逐字不变。只要正文有一个字变化，就不是 A4-1。

## 4. A4-2：仅修改正文某步

### 4.1 适用场景

正文某一步的写法变化，步骤编号与整体结构不变。典型场景：步骤缺失败分支、模糊词换条件句、输出示例补字段。A4-2 不处理步骤增删，不处理能力边界变化。

### 4.2 操作步骤

**第一步：定位到具体步骤编号，写清改前改后。** 不能只写“修了某步”，必须写“第 N 步，改前是什么，改后是什么”。改前改后要逐字对照，不能概括。

**第二步：检查该步的输入/产出是否被其他步骤引用，联动改。** 这是 A4-2 最关键的一步。某步的产出如果被后续步骤引用，改产出就必须改引用。检查方法：在全文中搜索该步的产出变量名或输出描述，逐条确认引用处是否仍然成立。

**第三步：version 次版本 +1。** 正文步骤变化属于产出形态变化，按次版本 +1 处理。

**第四步：从 S23 重跑结构校验，整体重跑不许局部。** 路径可以最小（只改一步），但验证必须整体。S23 是结构校验，重跑 S23 确认结构完整；然后整体重跑，确认产出形态没有意外变化。禁止只测改动涉及的那一条说法。

### 4.3 联动检查方法

联动检查的核心是“输入/产出引用”。具体做法：

1. 列出该步的输入变量和产出变量。
2. 在全文中搜索产出变量，找到所有引用处。
3. 逐条确认引用处是否仍然成立：变量名是否一致、类型是否一致、语义是否一致。
4. 如果引用处不成立，联动修改引用处，并重复第 3 步。

联动检查不能只查直接引用，还要查间接引用。某步的产出可能被中间步骤转换后再引用，转换链上的每一环都要查。

### 4.4 重跑策略

A4-2 的重跑策略是“路径最小、验证整体”。路径最小指只改需要改的那一步，不重复全量编辑；验证整体指改完后整体重跑，不局部重跑。整体重跑的范围包括：S23 结构校验、回归用例、产出形态对比。

禁止局部重跑的理由：局部重跑只能证明改动的那一条说法通过，不能证明联动没有破坏其他说法。A4-2 的风险恰恰在联动，局部重跑测不出联动问题。

### 4.5 常见错误

最常见错误是“改完就测改动那条，不测联动”。正确做法是改完后整体重跑，回归用例覆盖产出形态的原话。

## 5. A4-3：仅新增 reference

### 5.1 适用场景

主文件超预算，把某段细节外置为 references/ 下的独立文件。A4-3 只处理“外置”，不处理“新增能力”。外置的内容必须是主文件里已经有的内容，不能是新增内容。

### 5.2 操作步骤

**第一步：写清「该内容不能放主文件的理由」一句话理由。** 理由必须是具体的，判定口径“主文件已 4800 字，接近 5000 字上限，该段细节 600 字，只服务 5% 的场景”。不能写“为了整洁”这种模糊理由。

**第二步：主文件只留加载指令：按 references/X.md 的 Y 段组织内容。** 加载指令必须写明文件路径和段落定位，不能只写“见 references/”。加载时机也要写清：在什么条件下加载这个 reference。

**第三步：reference 内只讲一件事，标题可 grep。** 一个 reference 文件只服务一个主题，标题要能直接 grep 到。禁止一个 reference 文件塞多个不同主题。

**第四步：version 次版本 +1，S23 重跑校验引用路径真实存在。** 重跑 S23 时重点检查：主文件的加载指令路径是否存在、reference 文件的标题是否可 grep、加载时机是否写清。

### 5.3 reference 组织原则

reference 文件的组织原则：

1. **单一主题**：一个文件只讲一件事。
2. **标题可 grep**：标题要包含主题关键词，能直接被搜索到。
3. **自包含**：reference 文件不依赖主文件的上下文，单独读也能理解。
4. **加载时机明确**：主文件的加载指令要写清“什么时候加载”，不能无条件加载。

### 5.4 加载指令写法

加载指令的标准写法：

> 当 [触发条件] 时，按 references/X.md 的 [段落标题] 组织内容。

触发条件必须具体，不能写“需要时”。段落标题必须与 reference 文件内的标题一致，不能写模糊指代。

### 5.5 常见错误

最常见错误是“加 reference 时不写加载时机”。主文件只写“见 references/X.md”，没有触发条件，导致 reference 要么从不加载，要么无条件加载。两种都是缺陷。

## 6. 联动检查机制

### 6.1 三问详解

任何改动后，必须回答三问：

**第一问：引用的路径还真实存在吗？** 检查主文件里所有 references/ 路径、所有外部文件引用，逐条确认文件存在、路径拼写正确。

**第二问：步骤编号还连续吗？** 检查正文步骤编号是否从 1 到 N 连续，没有跳号、没有重号。A4-2 改动某步后，如果该步内部有子编号，子编号也要连续。

**第三问：待确认项还是原来那些吗？** 检查文档末尾的“待确认项”列表，确认改动没有引入新的待确认项，也没有把已确认项误标为待确认。

### 6.2 检查流程

三问的检查顺序：先查路径，再查编号，最后查待确认项。路径不过，后面的检查没有意义；编号不过，说明结构被破坏；待确认项不过，说明改动引入了未决问题。

三问全过才能进入交付。有一问不过，按对应步骤修，不许带病交付。

### 6.3 失败处理

路径不存在 → 回 A4-3 第二步，修加载指令路径。

编号不连续 → 回 A4-2 第一步，重新定位步骤编号。

待确认项变化 → 回改动起点，确认改动是否引入了新的未决问题。如果是，标为待确认项并写清原因；如果不是，修回原状。

## 7. 回归用例管理

### 7.1 用例来源原则

回归用例取自最初导致问题的那句用户原话，不是新编说法。这是 A4 的硬规则。新编说法只能作为补充用例，不能替代原话。

理由：原话是问题的真实触发条件，新编说法可能偏离真实场景。用新编说法做回归，可能测出一个“假通过”。

### 7.2 用例分类

A4-1 的回归用例必须针对触发面：原话、近义改写、反面场景。

A4-2 的回归用例必须针对产出形态：原话、产出形态的近义描述、产出形态的反面场景。

A4-3 的回归用例必须针对加载：触发加载的原话、不触发加载的原话、加载后产出形态的原话。

### 7.3 用例记录格式

用例记录格式：

> 用例编号 | 来源（原话/新编） | 原话文本 | 预期结果 | 实际结果 | 通过/失败

来源必须标“原话”或“新编”，不能省略。原话文本必须逐字记录，不能概括。

### 7.4 用例维护

回归用例随文档版本维护。每次 A4 改动后，新增的回归用例追加到用例库，不删除旧用例。旧用例若不再适用，标“已废弃”并写清废弃原因，不直接删除。

## 8. 禁止项及其风险分析

### 8.1 五项禁止

1. 局部改动后只测改动涉及的那一条说法。
2. 改 description 时顺手改正文。
3. 加 reference 时不写加载时机。
4. version 不升位就交付。
5. 改动记录只写「修了 bug」不写改前改后。

### 8.2 风险后果

**禁止 1 的风险**：局部改动可能破坏联动，只测一条测不出联动问题。后果是缺陷带进交付，下游使用时才暴露。

**禁止 2 的风险**：改正文会让产出形态变化，但 A4-1 的回归用例只覆盖触发面，测不出产出形态的破坏。后果是触发面通过、产出形态失败。

**禁止 3 的风险**：没有加载时机，reference 要么从不加载（内容丢失），要么无条件加载（主文件变相超长）。两种都是结构性缺陷。

**禁止 4 的风险**：version 不升位，下游无法判断当前版本是否包含修复。后果是版本追溯断裂。

**禁止 5 的风险**：改动记录只写“修了 bug”，无法判断改了什么、改动原因、影响面多大。后果是下一次改动无法做联动检查。

## 9. 失败分支处理

### 9.1 四类失败情形

| 情形 | 处置 |
| --- | --- |
| 改完重跑仍 FAIL | 停在 S23，定位到具体写法，再改 |
| 回归用例不命中 | 回 A4-1 第 3 步，从需求卡补该类原话 |
| 联动步骤漏改 | 回 A4-2 第 2 步，逐条查输入/产出引用 |
| 找不到最初问题原话 | 标「历史记录缺失」，用当前版本重跑，不拿旧记录充数 |

### 9.2 处置流程

失败分支的处置流程：先定位失败类型，再回对应步骤，修完后整体重跑，不允许局部重跑。

“改完重跑仍 FAIL”是最常见情形。处置要点是“停在 S23，定位到具体写法”，不能跳过 S23 直接改正文。S23 是结构校验，先过结构再改内容。

“找不到最初问题原话”是最难情形。处置要点是“标历史记录缺失，用当前版本重跑”，不能拿旧记录充数。旧记录可能对应不同版本，用它做回归会得出错误结论。

### 9.3 升级路径

如果失败分支处置后仍 FAIL，升级到完整流程。A4 只处理增量维护，不处理结构性缺陷。结构性缺陷必须回到 S1–S30 完整流程。

## 10. 输出前自检

### 10.1 自检清单

- [ ] 改动分类正确（三类之一）？
- [ ] version 升位与 CHANGELOG 一致？
- [ ] 回归用例取自最初问题原话？
- [ ] 联动三问全过？
- [ ] 重跑是整体重跑，不是局部重跑？

### 10.2 自检执行方式

自检在执行交付前逐项确认，不能凭印象打勾。每一项都要有对应的证据：改动分类要有 diff 记录，version 升位要有 CHANGELOG 条目，回归用例要有原话文本，联动三问要有检查记录，整体重跑要有重跑日志。

### 10.3 交付标准

五项自检全过才能交付。任一项不过，回对应步骤补齐，不进入交付。交付时附带：改动分类、version 变化、回归用例结果、联动检查记录、重跑日志。

## 11. 版本管理与变更记录

### 11.1 version 规则

A4-1（description 变化）：次版本 +1。A4-2（正文步骤变化）：次版本 +1。A4-3（新增 reference）：次版本 +1。主版本 +1 只用于能力边界变化，不属于 A4 范围。

### 11.2 CHANGELOG 格式

CHANGELOG 每条记录格式：

> version | 改动分类 | 改前 | 改后 | 回归用例结果 | 联动检查结果

“改前/改后”必须逐字记录，不能概括。“回归用例结果”必须列出每条用例的通过/失败。“联动检查结果”必须列出三问的检查结论。

### 11.3 变更追溯

变更追溯依赖 CHANGELOG 和 diff 记录。CHANGELOG 记录“改了什么”，diff 记录“具体怎么改”。两者缺一，追溯就不完整。

## 12. 总结

A4 手册的核心是四句话：**按改动类型走最小路径，但验证必须整体；联动检查三问全过才交付；回归用例取自最初问题原话；version 升位与 CHANGELOG 一致。**

最小路径省的是编辑时间，不是验证时间。验证必须整体重跑，因为增量改动的风险在联动，局部重跑测不出联动问题。

三问是联动检查的最小集：路径存在、编号连续、待确认项不变。三问有一问不过，就不交付。

回归用例的原话原则是防止“假通过”。新编说法可能偏离真实场景，只有原话能保证回归的有效性。

version 与 CHANGELOG 是追溯的基础。没有追溯，下一次改动无法做联动检查，A4 的最小路径就会退化成“盲改”。

A4 不处理结构性缺陷。结构性缺陷必须回到完整流程。A4 的边界清楚，才能保证增量维护不越界。
