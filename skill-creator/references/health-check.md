# 技能健康度体检（A3）专业规范

## 1. 引言：Skill 定期体检的定位

### 1.1 问题的提出

Skill 交付后不是终点。上线后可能因为平台检索口径变化、说法漂移、正文过期而慢慢失效。失效不是一次性的，而是渐进式的：第一周还能触发，第一个月触发面开始收窄，第一季度正文引用的 reference 路径已经过期。如果没有人定期检查，Skill 会在某个时刻“静默失效”——用户不会报告“Skill 坏了”，只会报告“Skill 不触发”，而后者更难定位。

A3 的目的，是给 Skill 一套定期体检流程：跑结构校验、跑触发代理测试、抽样看产出，三件事合成一份健康度报告。体检不是一次性的验收，而是周期性的维护。

### 1.2 与 A2、A4 的关系

A2 是交付前的平台适配检查，A4 是交付后的增量更新流程，A3 是交付后的周期性健康度体检。三者的关系：

- **A2 在建包时做**：检查 frontmatter 字段是否适配目标平台。
- **A3 在运行时做**：周期性检查 Skill 是否仍然健康。
- **A4 在改动时做**：增量改动后按最小路径更新。

A3 的体检结果，是 A4 增量改动的输入。体检发现 FAIL，按 A4 分类改动；体检发现 WARN，排入下次改动。没有 A3 的体检，A4 的改动就是“盲改”。

### 1.3 核心原则

A3 的四条原则：

1. **结果导向**：判定只看结果，不看感觉。“感觉还能用”不算数，必须有逐条证据。
2. **周期固定**：体检周期固定，不因“最近没出问题”而跳过。静默失效恰恰发生在“最近没出问题”的时候。
3. **定位到写法**：FAIL 项要定位到具体文件与写法，不能只写“结构有问题”。
4. **报告放包外**：体检报告放技能包外的 `tests/` 目录，与技能包平级，不进包。报告不进包，是因为报告是运行时产物，不是 Skill 的组成部分。

## 2. 体检项目详解

### 2.1 项目一：结构合规

**方法**：跑结构校验脚本 `scripts/validate_structure.py`，确认 0 FAIL。

**工具**：`scripts/validate_structure.py`。

**周期**：每次改动后。

**检查内容**：SKILL.md 的 frontmatter 字段是否完整、步骤编号是否连续、references 路径是否存在、文件结构是否符合规范。

**常见 FAIL**：frontmatter 缺字段、步骤编号跳号、references 路径拼写错误、文件缺失。

**修复路径**：按 A4 分类处理。frontmatter 缺字段 → A4-1；步骤编号跳号 → A4-2；references 路径错误 → A4-3。

### 2.2 项目二：描述合规

**方法**：跑完整校验脚本 `scripts/validate_skill.py`，检查 P001–P012 共 12 项规则。

**工具**：`scripts/validate_skill.py`。

**周期**：每次改动后。

**检查内容**：description 是否包含触发语、是否包含排除场景、name 是否规范、version 是否升位、多语言字段是否被误当主字段用。

**常见 FAIL**：触发语只写在 `description_zh`、name 用了大写、version 未升位。

**修复路径**：按 A4-1 处理。触发语迁移到主 `description`，name 改小写连字符，version 升位并写 CHANGELOG。

### 2.3 项目三：触发面

**方法**：三种说法代理测试，3/3 命中。

**工具**：`scripts/check_triggers.py`。

**周期**：每月一次。

**检查内容**：原话、近义改写、反面场景三种说法是否都能正确触发。原话验证修复是否生效，近义改写验证触发面是否过窄，反面场景验证排除面是否过宽。

**常见 FAIL**：2/3 命中（触发面过窄）、1/3 命中（触发语位置错误）、0/3 命中（Skill 完全失效）。

**修复路径**：停在本步，从需求卡补该类原话进 description，重跑三条。禁止只补一条就交付。

### 2.4 项目四：产出抽样

**方法**：抽最近 3 次真实产出，对照验收条件逐条核。

**工具**：人工。

**周期**：每月一次。

**检查内容**：交付物形态与「目标产出」字段一致、步骤四要素在产出里有体现、待确认项没有悄悄混进已确认内容。

**常见 FAIL**：文件名不符合目标产出、失败分支缺失、待确认项被误标为已确认。

**修复路径**：回对应步骤重写，禁用「下次注意」式处置。

### 2.5 项目五：引用新鲜度

**方法**：检查正文引用的 references 是否还存在、内容是否过期。

**工具**：人工。

**周期**：每季度一次。

**检查内容**：references 路径是否存在、reference 内容是否与主文件一致、reference 是否被主文件正确加载。

**常见 FAIL**：reference 文件被删除但主文件仍引用、reference 内容过期但主文件未更新、加载指令路径拼写错误。

**修复路径**：补文件或删引用，不许留悬空路径。按 A4-3 处理。

## 3. 健康度判定与处置

### 3.1 判定标准

| 结果 | 判定 | 处置 |
| --- | --- | --- |
| 5 项全过 | 健康 | 记录归档，不改包 |
| 1–2 项 WARN | 亚健康 | 逐条写保留理由，排入下次改动 |
| 任一项 FAIL | 不健康 | 定位到具体文件与写法，修复后整体重跑 |

### 3.2 判定原则

判定只看结果，不看感觉。具体含义：

1. **PASS 要有证据**：不能只写“通过了”，要写退出码、计数、测试得分。
2. **WARN 要有理由**：不能只写“待观察”，要写保留理由和计划修复时间。
3. **FAIL 要有定位**：不能只写“结构有问题”，要定位到具体文件和具体写法。

### 3.3 处置流程

**健康**：记录归档，不改包。下次体检周期到了再查。

**亚健康**：逐条写保留理由，排入下次改动。保留理由要具体，判定口径“触发面 2/3，反面场景未命中，根因是排除场景描述过窄，计划下次 A4-1 修复”。不能写“暂时没问题”。

**不健康**：定位到具体文件与写法，修复后整体重跑。修复按 A4 分类处理，重跑要整体重跑，不能局部重跑。

### 3.4 判定记录格式

判定记录格式：

> 判定 | 依据 | 处置 | 处置人 | 处置日期

判定必须与体检报告一起归档，不能只写“已处理”。

## 4. 产出抽样方法

### 4.1 抽样原则

抽最近 3 次真实产出，不抽自己编的样例。真实产出指实际使用 Skill 产生的交付物，不是测试用例。

### 4.2 抽样标准

每条产出对照三项：

1. **交付物形态与「目标产出」字段一致**：文件名、必含字段、格式是否符合目标产出的定义。
2. **步骤四要素在产出里有体现**：输入、动作、产出、失败分支是否在产出中可追溯。
3. **待确认项没有悄悄混进已确认内容**：待确认项是否仍标为待确认，没有被误标为已确认。

### 4.3 抽样记录

三条都符合记「通过」；有一条不符合记「不通过」并写根因。根因要具体，判定口径“文件名缺 version 后缀”“失败分支未写”“待确认项第 3 条被误标为已确认”。

### 4.4 抽样频次

每月一次，每次抽 3 条。如果 Skill 使用频率低，可以按“每 3 次使用抽 1 次”调整，但不能低于每季度 1 次。

## 5. 报告格式与归档

### 5.1 报告格式

```
# 健康度体检报告
日期：YYYY-MM-DD
技能包：<name>，version <x.y.z>

| # | 项目 | 结果 | 证据 |
| --- | --- | --- | --- |
| 1 | 结构合规 | PASS / FAIL | 退出码 + 计数 |
| 2 | 描述合规 | PASS / FAIL | 退出码 + 计数 |
| 3 | 触发面 | 3/3 / 2/3 / 1/3 / 0/3 | 三种说法得分 |
| 4 | 产出抽样 | 通过 n/3 | 不通过项根因 |
| 5 | 引用新鲜度 | 通过 / 不通过 | 过期引用列表 |

判定：健康 / 亚健康 / 不健康
处置：<对应第 3 节>
```

### 5.2 报告归档

报告放技能包外 `tests/` 目录，与技能包平级，不进包。报告命名格式：`health_YYYY-MM-DD.md`。

### 5.3 报告追溯

报告按日期归档，不覆盖旧报告。追溯时按日期查找，看健康度变化趋势。趋势比单次报告更有价值：连续三次亚健康说明有系统性问题，单次 FAIL 可能只是偶发。

## 6. 边界与局限

### 6.1 业务内容不验

体检只验产出物结构与触发面，不验业务内容对错。业务对错由使用者判断。Skill 无法判断“这个产出是否解决了用户的问题”，只能判断“这个产出是否符合目标产出的定义”。

### 6.2 代理测试不等于真实召回

代理测试通过不等于平台真实召回。平台实测仍需按里程碑 4 在真实会话中做。代理测试是“预检”，不是“终检”。

### 6.3 报告不进包

体检报告放技能包外 `tests/` 目录，与技能包平级，不进包。报告是运行时产物，不是 Skill 的组成部分。进包会导致包体积膨胀，也会导致报告被误认为 Skill 内容。

### 6.4 平台差异不覆盖

A3 不覆盖平台差异，平台差异由 A2 处理。A3 的触发面测试是代理测试，不区分平台。平台实测在里程碑 4 做。

## 7. 失败分支与升级路径

### 7.1 四类失败情形

| 情形 | 处置 |
| --- | --- |
| 结构校验 FAIL | 修结构，改完整体重跑，不许只补人工项 |
| 触发面 2/3 或更低 | 停在本步，从需求卡补该类原话进 description，重跑三条 |
| 产出抽样不通过 | 回对应步骤重写，禁用「下次注意」式处置 |
| 引用过期 | 补文件或删引用，不许留悬空路径 |

### 7.2 处置流程

失败分支的处置流程：先定位失败类型，再回对应步骤，修完后整体重跑，不允许局部重跑。

“修结构，改完整体重跑”是最常见情形。处置要点是“整体重跑”，不能只补人工项。人工项只能覆盖已知问题，覆盖不了联动问题。

“停在本步，补原话进 description”是最容易走偏的情形。处置要点是“从需求卡补该类原话”，不能自己编新说法。新说法可能偏离真实场景，测出“假通过”。

### 7.3 升级路径

如果失败分支处置后仍 FAIL，升级到完整流程。A3 只处理周期性体检，不处理结构性缺陷。结构性缺陷必须回到 S1–S30 完整流程。

## 8. 输出前自检

### 8.1 自检清单

- [ ] 五项都做了，有记录？
- [ ] FAIL 项定位到具体文件与写法？
- [ ] 报告写清了判定与处置？
- [ ] 报告放包外 tests/？

### 8.2 自检执行方式

自检要逐项确认，不能凭印象打勾。每一项都要有证据：五项记录要有报告表格，FAIL 定位要有文件路径与行号，判定与处置要有对应段落，报告位置要有目录截图或路径说明。

### 8.3 交付标准

四项自检全过才能交付。任一项不过，回对应步骤补齐，不进入交付。交付时附带：体检报告、判定记录、处置记录。

## 9. SKILL：健康度体检的自动化实现

### 9.1 SKILL 的定位

A3 的体检项目可以人工做，也可以做成 SKILL 自动化。SKILL 化的目的是：把重复性检查固化为可执行脚本，把判定逻辑固化为规则，把报告生成固化为模板。人工只做无法自动化的部分（产出抽样、引用新鲜度的人工判断）。

### 9.2 SKILL 的输入

SKILL 的输入：

1. **技能包路径**：包含 SKILL.md、references/、scripts/ 的目录。
2. **体检项选择**：全量体检或单项体检。
3. **历史报告路径**：可选，用于趋势对比。
4. **需求卡路径**：可选，用于触发面测试的原话提取。

### 9.3 SKILL 的执行流程

**第一步：结构校验**。调用 `scripts/validate_structure.py`，捕获退出码和计数。退出码非 0 记 FAIL，退出码 0 记 PASS。

**第二步：描述合规**。调用 `scripts/validate_skill.py`，捕获 P001–P012 的检查结果。有 FAIL 记 FAIL，有 WARN 记 WARN，全 PASS 记 PASS。

**第三步：触发面测试**。调用 `scripts/check_triggers.py`，传入三种说法（原话、近义改写、反面场景）。3/3 记 PASS，2/3 记 WARN，1/3 或 0/3 记 FAIL。

**第四步：产出抽样**。从历史产出目录抽最近 3 条，逐条对照三项验收条件。无法自动化的部分（如“待确认项是否被误标”）标记为“需人工确认”。

**第五步：引用新鲜度**。扫描主文件中的所有 references 路径，逐条检查文件是否存在。无法自动化的部分（如“内容是否过期”）标记为“需人工确认”。

**第六步：生成报告**。按报告格式生成 Markdown 文件，写入 `tests/` 目录。

**第七步：判定与处置**。按判定标准给出健康/亚健康/不健康，按处置流程给出处置动作。

### 9.4 SKILL 的失败处理

**脚本调用失败**：捕获异常，记 FAIL，报告中写清失败原因（如“validate_structure.py 不存在”）。

**脚本超时**：记 WARN，报告中写清超时时间，转人工检查。

**报告写入失败**：记 FAIL，报告中写清写入路径与错误信息，不吞异常。

**判定规则冲突**：如果某项既有 PASS 又有 WARN，按“最严原则”记 WARN。如果某项既有 WARN 又有 FAIL，记 FAIL。

### 9.5 SKILL 的集成方式

SKILL 可以三种方式集成：

1. **独立运行**：作为独立脚本，手动调用。
2. **CI 集成**：在 CI 流水线中，每次提交后自动跑结构校验和描述合规。
3. **定时任务**：每月自动跑触发面和产出抽样，生成报告并通知。

### 9.6 SKILL 的版本管理

SKILL 的版本与 A3 手册的版本同步。A3 手册更新时，SKILL 的检查规则同步更新。版本记录写入 SKILL 的 CHANGELOG，不与技能包的 CHANGELOG 混用。

### 9.7 SKILL 的自检清单

- [ ] 输入路径存在？
- [ ] 五个体检项都执行了？
- [ ] 报告格式符合模板？
- [ ] 判定规则按最严原则？
- [ ] 报告写入包外 tests/？

### 9.8 SKILL 的局限性

SKILL 只能做自动化检查，不能替代人工判断。产出抽样的“待确认项是否被误标”、引用新鲜度的“内容是否过期”，仍需要人工确认。SKILL 的输出是“预检报告”，不是“终检报告”。

## 10. 与 A4 增量更新的衔接

### 10.1 A3 结果作为 A4 输入

A3 体检发现 FAIL，按 A4 分类处理：frontmatter 问题 → A4-1；正文步骤问题 → A4-2；references 问题 → A4-3。A3 体检发现 WARN，排入下次 A4 改动。

### 10.2 A3 周期与 A4 周期的协调

A3 的体检周期（每月/每季度）与 A4 的改动周期（按需）协调。A3 体检后如果有 FAIL，A4 改动后要重跑 A3 的结构校验和描述合规，不需要重跑触发面和产出抽样（除非改动涉及触发面）。

### 10.3 回归用例的继承

A3 触发面测试的三种说法，可以作为 A4-1 的回归用例基础。A4-1 改 description 时，复用 A3 的三种说法，不重新编造。

## 11. 版本管理与变更记录

### 11.1 A3 手册版本

A3 手册每次更新，version 升位并写 CHANGELOG。CHANGELOG 记录：变更项、变更前、变更后、变更依据。

### 11.2 体检报告版本

体检报告按日期归档，不覆盖旧报告。每次报告记录：技能包 version、体检日期、判定结果、处置记录。

### 11.3 趋势记录

趋势记录按季度汇总：健康次数、亚健康次数、不健康次数、主要 FAIL 类型。趋势记录用于判断是否有系统性问题。

## 12. 总结

A3 手册的核心是四句话：**五项体检固定周期，判定只看结果不看感觉，FAIL 定位到具体写法，报告放包外 tests/。**

A3 的价值在于把“Skill 是否还健康”从主观判断变成客观检查。五项体检覆盖结构、描述、触发面、产出、引用五个维度，每个维度都有明确的检查方法和判定标准。

A3 的 SKILL 化，把重复性检查固化为可执行脚本，把判定逻辑固化为规则，把报告生成固化为模板。人工只做无法自动化的部分，SKILL 做可自动化的部分。

A3 的边界清楚：不验业务内容对错、代理测试不等于真实召回、报告不进包、平台差异不覆盖。边界清楚，才能保证体检不越界、不遗漏、不擅自断言。

A3 与 A2、A4 的关系：A2 建包时做平台适配，A3 运行时做定期体检，A4 改动时做增量更新。三者形成闭环，Skill 才能在长期运行中保持健康。
