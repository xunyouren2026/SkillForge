# skill-creator 项目深度教程
本文件是 skill-creator 项目的内部说明书。它不指导怎么生成一个新技能——那是 `skill-creator` 本体的事；它解释这个项目**为什么长成这样**、每个部件的判定依据是什么、以及哪些设计是踩坑之后改出来的。读这份文件的对象是 AI。假定读者已经会用命令行、能读 Python 与 Markdown，但不假定读者知道本项目的历史。

## 第 0 章　怎么用这份文件
本教程分三层，建议按需跳读：

**第一层是机制层**（第 1 至第 5 章）。讲清 Skill 生产流水线本身：六环节各自解决什么问题、四套校验体系各自拦什么错、判定阈值为什么是这个数字。这一层决定读者能否正确执行与修改本项目。

**第二层是理由层**（第 6 至第 9 章）。讲清那些看起来奇怪的设计背后的理由。校验器里的槽位判定、职责段截断、反向夹具这些做法，不解释就会被人当成过度设计改掉。

**第三层是教训层**（第 10 章）。本项目开发过程中真实踩过的坑及其修法。这一章的每一条都是已经付出过代价的结论，改动本项目前应当先读。

配套资料在包外，不在本文件内：

- `references/` 存放方法文档，是流水线的执行细则，按环节加载。
- `scripts/` 存放六个校验与体检脚本，可直接执行。
- 包外的 `tests/` 存放夹具与回归记录，不进技能包。

## 第 1 章　这个项目要解决什么问题
先说清问题，否则后面所有设计都显得刻意。写一个 Skill 包这件事，门槛低得可疑。创建一个目录，放一个 SKILL.md，写几段步骤说明，完事。软件作者在两小时内就能交出一个"能用"的技能包。问题恰恰在这里：**它能跑，但它不知道自己什么时候该被触发、触发之后做出来的东西对不对、以及半年后还有人维护吗。**这三个问题对应三类失败：

**触发失败**是最隐蔽的一类。用户需要这个技能，但技能没有被召回，用户得到的是模型临场发挥的答案。技能内容写得再好也没用，因为压根没被加载。这类故障没有任何报错，只是"效果不如预期"，排查成本极高。

**产出失败**是第二类。技能被正确触发了，但产出的东西不符合预期：漏了一个字段、跳过一个边界条件、失败了不报错而是硬着头皮往下做。这类故障靠人眼能发现，但每次都要人肉检查，不可规模化。

**腐化失败**是第三类，也是最少被认真对待的一类。技能交付时是好的，三个月后平台检索口径变了、正文里引用的文件被删了、description 里的触发语过时了。技能还在那儿，但已经不触发，或者触发了就跑不通。这类故障没有任何人会主动报告——用户只会说"这个技能好像不太好用了"，而这句话往往会被误解为"模型变笨了"。

skill-creator 项目的全部结构，都是在拦这三类失败。

### 1.1 一句话定位
把一句用户需求转成可部署的 Skill 包（六环节流水线），并用四套可执行的校验体系证明这个包**能触发、产出合规、结构合法、语义干净**。注意"证明"两个字。本项目不信"我觉得没问题"，只信脚本跑出来的 PASS/FAIL 计数与退出码。任何一条判定都必须能定位到具体文件与行号，任何一条 PASS 都必须附证据。这是本项目与普通文档写作最大的分野。

### 1.2 人类在什么位置介入
流水线全程六环节，人类只在两个节点介入：

**需求确认**（环节二末尾）。AI 采集完需求卡后交人类确认，八个字段逐条过一遍。这一步拦的是"AI 理解错了需求"。位置在这里，是因为需求理解错误的修复成本最高——需求卡错了，后面五个环节全白做。

**交付确认**（环节六末尾）。所有校验跑完、自检清单判完、待确认项列完之后，交人类接收。这一步拦的是"校验通过了但其实不好用"。位置在最后，是因为人能看出的问题大多需要看到成品全貌才判断得出来。

除此之外的四个环节自主执行，不打断。这是刻意的：介入点越多，人越容易疲劳，疲劳的确认等于没确认。

### 1.3 一个明确的边界
本项目不覆盖三件事：平台 UI 操作与账号授权、复杂工程集成、平台真实召回的调优。前两件是能力边界——写不了就别装。第三件更微妙：真实召回由平台的调度算法决定，本项目能做的只是让 description 尽可能贴近真实用户说法，并提供一套本地代理测试来发现结构性漏词。这两者不是一回事，第 8 章会详细讲这个区别，以及为什么本项目坚持把"代理测试通过"和"平台实测通过"分开表述。

## 第 2 章　项目结构全景
```
SkillForge/
├── SKILL.md                    # 根目录入口，内容与 skill-creator/SKILL.md 一致
├── skill-creator/              # 技能包源包
│   ├── SKILL.md                # 六环节流水线主文件，132 行
│   ├── references/             # 15 份方法文档（核心 7 + 扩展 8）
│   ├── assets/                 # 3 份模板（需求卡、六段骨架、CHANGELOG）
│   └── scripts/                # 6 个脚本
├── dist/skill-creator/         # 分发副本，与源包逐文件哈希一致
├── docs/                       # 项目说明与完整技能描述
├── examples/                   # 4 个完整成品范例
└── tests/                      # 全部测试资产，与技能包平级
```

先解释几个看起来可以省掉但实际不能省的设计。

### 2.1 为什么有源包和分发副本两份
`skill-creator/` 是开发时直接改的源包，`dist/skill-creator/` 是对外分发的干净副本。两者内容逐文件哈希一致。

看起来是冗余，实际上解决两个具体问题。一是分发时不需要考虑源包里可能存在的中间状态（改了一半的文件、临时脚本、调试残留），直接给 dist 就不会把开发痕迹带出去。二是回归检查器 `tests/feature_check.py` 固定校验 dist 副本，等于在每次回归时验证"将要发出去的那一份"是合法的，而不是验证"我正在改的那一份"。项目里曾经出过源包残留 Windows 挂起空目录的问题（references 目录下多出一层同名子目录），dist 副本因为是程序化复制出来的，从不带这类残留。分两份的收益在这种时候就体现出来了。

### 2.2 为什么测试资产必须在包外
这是硬约束，不是风格偏好。技能包会被分发、被安装、被平台加载，包内的每个文件都占用上下文预算，都可能被人误读为技能内容的一部分。所以本项目的划分是：包内只放**运行时会用到的东西**（可执行脚本与方法文档），包外 `tests/` 放**验证运行时的东西**（说法清单、夹具、走查记录、回归报告）。具体来说，一个技能包目录里不允许出现 `tests/`、`test/`、`fixtures/` 这三个目录名——这是结构校验 S008 的判定项。也不允许出现空目录（S003）、占位文件（S004）、未替换的花括号占位标记（S004）。

### 2.3 六个脚本各管一段
```
validate_structure.py   # S001–S011，包体形态
validate_skill.py       # P001–P012，内容合规
check_triggers.py       # 触发覆盖代理测试 + 负样本误触发检测
check_semantics.py      # 语义项自检，29 项中 14 项自动判定
health_check.py         # 健康度体检 A3 五项 + 报告生成
analyze_usage.py        # 调用日志用量分析
```

这六个文件都放在 skill-creator 包的 scripts 目录下，本教程包不重复收录——教程讲的是方法，脚本本体属于被讲解的那个包。

前两个是交付前的硬校验，中间两个是交付前与维护期都能跑的判定，最后两个是维护期的辅助工具。六个脚本**只依赖 Python 标准库**，不用第三方包。这不是洁癖：校验器要能在任何装了 Python 的机器上直接跑起来。如果校验器自己需要先装依赖才能跑，那它就成了一个新的故障源——用户报的问题会是"跑不动你的校验脚本"，而不是"你的技能包有问题"。同样地，所有脚本**只读**，不修改被检目录。唯一的例外是 `health_check.py` 会写一份报告到包外 `tests/`，因为报告是它被要求产出的东西。

## 第 3 章　六环节流水线：每一步在解决什么
流水线的形态是：准入判定 → 需求采集 → 触发描述生成 → 结构决策 → 正文生成 → 校验与交付。环节顺序不是随意排的，它是一条**信息递减**的链：先确定"要不要做"，再确定"给谁做什么"，然后才确定"怎么触发"（依赖前面才知道的产出形态）、"文件怎么组织"（依赖触发面的宽度）、"正文怎么写"（依赖目录结构），最后校验。倒过来做必然出问题。先写正文再补 description，会发现触发语只能迁就正文已有的措辞，而正文里的措辞是随手写的；先定目录再定正文，会发现步骤该拆还是该并还没想清楚。每一环都是下一环的输入。

### 3.1 环节一：准入判定
四项核对，命中 ≥3 项才继续：

| 判据 | 判定标准 |
| --- | --- |
| 复用性 | 同类任务预期 ≥3 次 |
| 非显然性 | 含模型推不出的规则 |
| 可判定产出 | 有可验收的交付物 |
| 步骤化 | ≥3 个有序且依赖的步骤 |

这四项各自堵一个漏洞。

**复用性**堵的是"这个需求只值得做一次"。一次性的任务写成技能，收益低于成本——配置成本、上下文成本、维护成本都是实打实的。

**非显然性**是本环节最关键的一条。模型本身很强，很多事它直接就能干。如果一个需求的全部内容是"帮我把这段代码翻译成英文"，那它不需要 Skill，模型本来就干得不错。Skill 的价值恰恰在于**固化模型推不出的规则**：某个团队的特定命名规范、某套只在特定场景成立的操作顺序、某个必须问用户才能确定的口径。

**可判定产出**堵的是"做完之后说不清算不算做好了"。如果产出物无法逐条验收，那么后面所有校验都无从谈起——校验器需要一个明确的验收标准才能写。

**步骤化**堵的是"其实一句话就能说清"。如果流程只有一步，那它不是流程，是一句提示词。这种需求更适合给一段提示词而不是建一个包。

四项命中 ≤2 时，输出终止结论并给替代方案：一段提示词、一个脚本、一个模板、或人工做一次。这不是拒绝服务，是把需求导向成本更低的形态。拒绝时必须说清理由，不能只说"这个不适合做成 Skill"。

### 3.2 环节二：需求采集
采集两轮，产出八字段需求卡。第一轮只采集触发相关：会怎么开口触发（要原话）、什么任务、谁发起、多久一次。最多三问。第二轮采集交付与边界：最终交付什么（具体到文件名与字段）、明确不做什么、哪些相邻需求不误触发。最多三问。八字段是：服务对象、真实场景、触发原话、目标产出、关键约束、不做什么、相邻易混淆需求、待确认项。

两个设计要点：

**触发原话要"原话"，不能改写。** 用户说"下次别让我从头讲一遍"，就把这句话原样写进需求卡。这句话随后会原样进 description，成为触发语。改写成"请避免重复说明需求"会丢掉口语特征，而口语特征恰恰是触发匹配的关键——真实用户下一次说的还是那句口语。

**相邻易混淆需求是负样本的来源。** 需求卡里写清"哪些相邻需求不该触发我"，这一项在环节三直接变成 description 的排除场景，在环节六直接变成负样本清单。同一个信息在一处采集、三处使用，避免了三处口径不一致。

缺口按字段逐个补问，已填字段不重复问。人类连续两次不确认，判定需求不清楚，输出"先用一段提示词试一次"及提示词骨架，流水线终止。

### 3.3 环节三：触发描述生成
产出 description，格式是三段式：

```
[做什么：动词 + 对象 + 可验收产出]
+ [什么时候用：任务场景 + ≥3 条「」用户原话 + ≥1 个可识别对象]
+ [不覆盖什么：排除场景 + 相邻需求归属]
```

这一环是整个流水线里最难写对的，因为 description 是**唯一的检索入口**。平台在决定是否加载一个技能时，看的就是 name 和 description 两行字。主文件写得再好，description 没写好，技能等于不存在。三段式里第二段最关键。**触发语必须用「」包起来，并且是用户会说的原话。** 至少三条，覆盖三类：

| 类型 | 定义 | 例子 |
| --- | --- | --- |
| 口语型 | 生活措辞，可含"技能" | 我想做个 Skill |
| 术语型 | 含显式术语 | SKILL.md 怎么写 |
| 无术语型 | 不提 Skill、技能与 description 这些词，只描述痛点 | 下次别让我从头讲一遍 |

三类都要有，是因为平台召回可能走三条不同的路：语义相似、关键词匹配、以及"这句话本身像不像在要这个技能"。只写术语型，语义匹配的路就断了。硬关六项是这一环的判定门槛：第三人称、单行、≤1024 字符、≥3 条「」原话、≥1 个可识别对象、写清不做什么、七个禁词零出现。

七个禁词是：帮助、辅助、相关、各种、提升效率、智能化、一站式。它们不是"不好的词"，是**没有信息量的词**。写"帮助你高效地管理客户反馈"，读者（无论是模型还是人）得不到任何可判定的信息；写"把客户反馈按问题类型归类，输出 feedback-triage.md（归类维度、判定条件、无法归类处置、输出字段）"，信息就足够判定了。第三段"不覆盖什么"常被写成废话。合格的排除句要指向具体能力，并写明相邻需求归属谁："不覆盖舆情监测、竞品分析；相邻的代码 lint 归属 SonarQube"。这种写法在负样本检测里能直接生效——排除句里的词不会被算作召回依据。

### 3.4 环节四：结构决策
先输出默认最小集——只有 SKILL.md。然后问三个问题：

| 问题 | 答"是"才加 |
| --- | --- |
| 有大量细节用到才读，放主文件会挤占常驻上下文？ | `references/` |
| 有确定性操作要可复现？ | `scripts/` |
| 有要复制填充的模板？ | `assets/` |

每个非默认目录要写一句理由，格式固定：`[路径] → 不能放主文件的理由 + 加载/执行时机`。理由不合格就删目录重来。**不合格的表述包括"更规范""惯例""更专业""方便扩展"**——这四个词没有任何可判定性，等于没写。合格的理由长这样："`references/` → 格式判定规则有 40 行，只在 S5 判级时读一次，放主文件会挤占常驻上下文"。

行数预算同时算：目标 ≤300 行，上限 500 行。超 300 定位超支段只外置该段，超 500 必须拆分。三问的第一问有个反直觉的判定标准："单段内容超过主文件预算 15%，或只在某一步加载"。按比例算比按绝对行数算准，因为 40 行规则放在一个 100 行的技能里是灾难，放在一个 400 行的技能里无所谓。

### 3.5 环节五：正文生成
六段骨架，顺序固定：目标 → 前置 → 步骤 → 输出示例 → 禁止项 → 常见错误。每步四要素，缺任一行判该步不合格：

| 要素 | 格式 | 判定标准 |
| --- | --- | --- |
| 输入 | 文件名或字段名 | 写到能定位的程度 |
| 动作 | 动词开头 | 一条动作一个动词，不含态度词 |
| 产出 | 文件名 + 字段清单 | 字段名与输出示例一致 |
| 失败分支 | 当 `[可观测条件]` 成立时，退回 `[环节]`，补 `[内容]` | 条件可判真假 |

失败分支是四要素里最常被漏掉、也最重要的一项。一个只会成功路径的技能，遇到异常时模型会自己发挥——编一个数、跳过一步、或者直接说"已完成"。**失败分支把"模型临场发挥"变成了"流程内可预期行为"**。模糊词替换表把不可判定的表达换成可判定的：必要时、酌情、视情况、灵活处理、适当、根据实际情况。每一项都有替换格式，例如"必要时 [动作]"换成"当 [可观测条件] 成立时，执行 [动作]"。语体五条：祈使句、无主句、无营销词、一处定义（同一字段只定义一次）、编号连续不跳号。

### 3.6 环节六：校验与交付
按顺序跑三件事：结构校验（11 项，0 FAIL 才继续）、触发测试（三说法全中才继续）、自检清单逐项判三态。跑完整理四块交付物：目录树、SKILL.md 全文或路径、自检结论、待确认项。

四块给齐且人类确认接收，流水线终止。这条停止条件写死在主文件里，是为了防止无限循环——对产出物再跑一遍流水线、对自检结论再做自检、对校验脚本写校验脚本，这三种行为在实践中都发生过，且都会导致无限递归。失败退回规则由 skill-creator 包内的回退总表统一管理：环节间不循环、不回跳，只按失败分支退回指定环节。同一失败条件连续触发两次，退回上一环节，退回原因写入自检结论。

## 第 4 章　四套校验体系：各自拦什么错
本项目有四套互相独立的校验。它们不是同一件事的四次重复，而是四种不同性质的门：包体形态门、内容合规门、触发面门、语义洁净门。四道门都过，技能包才算可交付；任何一道门不过，退回路径不同。

### 4.1 结构校验 S001–S011：包体形态
`validate_structure.py` 检查十一项，全部只读、只用标准库。它回答的问题是"这个包的物理形态合法吗"。

S001 查 SKILL.md 存在，确立最小集基线——一个技能包至少要有主文件。S002 查主文件行数，目标 300 行、上限 500 行，超上限 FAIL、超目标 WARN。S003 查空目录，因为空目录往往意味着建目录时规划了结构但内容没落地。S004 查占位文件与未替换的花括号占位标记，这是模板复制后最常见的遗留。

S005 查目录名是否在允许列表内（references、scripts、assets、examples 四个）且为小写复数。S006 查主文件引用的资源路径是否真实存在——这条拦的是"正文里写得像模像样提到某个 references 下的文件名，但那个文件根本不存在"。S007 查是否用了绝对路径或工作区相对路径，因为技能包要被复制到任意位置使用，写死路径等于埋雷。

后四项是安全向的。S008 查包内是否有测试目录，把测试资产隔离在包外。S009 查 allowed-tools 有没有全通配（`Bash(*)` 或裸 `Bash`），全通配等于把整个系统交出去。S010 查 scripts/ 下有无敏感系统路径（系统配置目录、SSH 密钥目录、用户主目录），S011 查有无硬编码密钥模式。这十一项里没有一项需要理解技能的业务内容。它们全部是形状检查，因此可以做到完全确定性、零误判、秒级完成。

### 4.2 内容校验 P001–P012：内容合规
`validate_skill.py` 检查 frontmatter 与正文表述。它回答的问题是"这个技能写得像不像一个合格的技能"。

P001 查 frontmatter 结构完整，`---` 正确包裹。P002 查 name 规范（小写字母数字连字符、≤64 字符）且与目录名逐字一致——不一致会导致分发时目录改名而 name 没改，技能加载失败。P003 查 description 存在、单行、≤1024 字符。P004 查 description 叙述部分的人称，叙述部分须第三人称或无主句。

P005 查触发语覆盖：至少三条「」原话，且不能全是术语型（否则语义匹配这条路断了）。P006 查正文引用的资源路径存在。P007 查占位符与槽位残留。P008 查行数在预算内。P009 查 description 有无空信息词（那七个禁词的扩展表）。P010 查排除场景。P011 查目录规范。P012 查存在资源索引或加载路由表。P004 与 P005 都处理了「」内的用户原话——那句"帮我"是第一人称，但它是被收录的用户话语，不是技能自己的叙述。判定前先剔除「」内容再做人称检查，避免误报。

### 4.3 触发测试：正样本加负样本
`check_triggers.py` 做两件事。

**正样本**验"该触发的触发了"。做法是把用户原话与 description 做字符二元组重合度计算：归一化只保留 CJK 与 ASCII 字母数字、字母小写，取所有相邻二元组，算交集占说法全集的比例。得分 ≥0.30 判命中，0.18–0.30 判边缘，<0.18 判未命中。

description 里「」包住的短语作为说法子串时给加成，但**加成按比例给不是固定值**：加成基数 0.35 乘以「触发语长度占说法长度的比例」。说完整等于某条触发语时拿满 0.35，只命中长触发语的一小段时按比例折减。固定加成的问题在于长触发语配短说法会虚假满分，那样测出来的"全中"不含信息量。

**负样本**验"不该触发的没触发"。做法是对相邻需求说法算同样的分，高于混淆阈值即判误触发风险。这套能力是本项目后期补上的，补的动因见第 8 章。

### 4.4 语义项自检：29 项中的 14 项
`check_semantics.py` 处理那些**能判定但不属于形态**的规则。完整的人工清单有 29 项，分布在三组：人工清单 12 项、安全判据 3 项、合规检查 7 项、安全审查 7 项。剩下 15 项依赖人类确认、跨文件比对或平台外部信息，仍然人工判。

能自动化的 14 项是：第 8 项（每步四要素齐全、模糊词零命中）、第 9 项（脚本仅标准库）、第 10 项（输出示例字段表与禁止项/常见错误表结构）、第 14 项（密钥、内网地址、真实用户信息零命中）、第 16 项（第三方原文与版权声明标记）、第 18 项（手机号/身份证号/邮箱/银行卡形态零命中）、第 21 项（敏感内容零命中）、第 22 项（依赖仅标准库）、第 23 项（三个资源目录里无指令性注入文字）、第 24 项（allowed-tools 无全通配）、第 25 项（脚本与示例无真实路径、内网地址、密钥）、第 27 项（无明文密钥、密钥读取走环境变量）、第 28 项（无网络调用、无 shell 调用）、第 29 项（写盘路径落在技能根目录内）。

每条判定输出 PASS / WARN / FAIL 三态并附可定位证据。语义项与结构项的口径差别在于：结构项是二值判定，语义项有"需人工确认"这个中间态。比如第 16 项许可与版权，脚本只能检出第三方原文标记，许可来源清单仍然要人确认，这时正确输出是 WARN 而不是 PASS。

### 4.5 健康度体检 A3
`health_check.py` 是维护期工具，把体检方法论的五项固化为脚本：结构合规、描述合规、触发面、产出抽样、引用新鲜度。前三项复用已有校验器，第四项自动检查产出目录里每个 SKILL.md 的步骤编号连续性与四要素齐全，第五项检查主文件引用的资源是否都存在且非空。

五项结果按最严原则合成一个判定：全 PASS 是健康，1–2 项 WARN 且无 FAIL 是亚健康，任一项 FAIL 是不健康。退出码 0/1/2 对应这三种。报告写到包外 `tests/health_<日期>.md`。体检脚本本身有个设计要点：它编排其他脚本时用 `subprocess` 调用同包内的校验脚本，这是合法用法。因此第 28 项的判据是"有无 shell 调用与 `shell=True`"，而不是"有没有 import subprocess"。把编排能力判成违规，等于禁止体检脚本存在。

## 第 5 章　内容校验的两个精细判据
P007 的槽位判定与负样本的职责段截断，是本项目里唯二需要额外解释的判据。它们都属于"朴素实现会误杀合法内容"的情况。

### 5.1 槽位判定：占位符残留的正确理解
朴素实现是查正文里有没有 `TODO` 这个子串。问题在于 `TODO` 可能是业务对象而非残留标记。实测中就撞上过：一个扫描待办注释的技能，产出文件名必须叫 `TODO-INDEX.md`，正文里还要写"六种标记词：FIXME / HACK / XXX / BUG / NOTE / TODO"。朴素的子串检查把这两处全判成残留，第一次产出必然 FAIL，被迫把产出格式外置到 references、正文改写为引用才能通过——为一个字符串检查付出结构上的代价。

正确做法是判**语法位置**而不是判**子串出现**。标记词处于尚待填写的槽位才算残留，行末的 `TODO:`、行尾单独的 `TODO` 算残留；而产出文件名 `TODO-INDEX.md`、说明句"按 TODO 关键字匹配"、代码块内的示例，都不算。三条豁免规则支撑这个判定。第一，行内代码（反引号包裹）内的标记词是引用，不参与判定。第二，围栏代码块内的内容是示例，不参与判定。第三，一批通用槽位词（表示"此处还缺内容"的固定措辞）本身即残留信号，不看位置。

实现上还有一个细节：判定按行做，先剥掉行内代码与围栏代码块，再匹配槽位正则。槽位正则要求标记词前后不是单词字符或连字符（避免 `TODO-INDEX` 被当成裸 TODO），且后面接冒号或行尾。

### 5.2 职责段截断：排除句不能算召回
负样本判定需要算"这句话与技能有多像"。朴素做法是拿整条 description 算，包括排除句。问题是排除句写的是"本技能不做什么"，它是用来**排斥**的，不是用来吸引的。实测中"帮我登录这个账号"被判成误触发，得分 0.429——超过命中阈值 0.30 的原因，是"账号"这个词来自排除句「不覆盖平台 UI 操作与账号授权」。用排除句的词去证明"这句话该被这个技能接住"，方向是反的。

修法是先截掉排除句，只留职责段（做什么 + 什么时候用）参与负样本计算。截断依据是排除句的起始标记词（不覆盖、不用于、不涉及、不适用于、不处理、不做、排除），取最早出现的位置。修完该条降到 0.286，回到正常区间。

### 5.3 阈值为什么是 0.40
负样本的混淆阈值定在 0.40，高于正样本的命中阈值 0.30。这个差值不是随手填的。负样本已经剔除了排除句，剩下的词面重叠多来自职责段里的动词与名词——"代码质量扫描"与"扫描代码注释"共享"扫描""代码"，"生成 issue"与"生成索引"共享"生成"。这类重叠是语言现象，不等于会误触发。要判风险，重叠得更高。

这里还有一个更重要的判据选择问题。最初的设计是"负样本得分 ≥ 正样本最低得分即判误触发"，用相对阈值。但这个设计是失效的：正样本的说法直接取自 description 的触发语，纯覆盖率必然等于 1，拿它当基准则 bar 恒为 1.0，任何负样本都判不了误触发——**判据退化成永真通过，比原缺陷更危险，因为它看起来在工作**。所以最终用固定阈值 0.40 比较**纯覆盖率**（不含触发语加成）。不用最终得分比较，是因为最终得分含加成，正样本常因此拿满 1.0。

### 5.4 反向夹具：防止判据退化
以上两个判据都有"看起来在工作，实际已经不工作"的风险。为此本项目引入反向夹具机制。反向夹具是**故意构造的违规包**，放在 `tests/` 下，必须被检测器报出 FAIL。如果某个反向夹具恒定通过，说明判据退化成了永真通过，回归检查器直接判 FAIL。

现有四个反向夹具各对应一类退化风险：`structure-fixtures/over-trigger` 的 description 用词宽泛，负样本与它高度重叠，必须报出误触发；`structure-fixtures/slot-words` 含真实槽位残留，P007 必须报 FAIL；`structure-fixtures/legal-marker-ref` 含合法引用，P007 必须报 PASS；`semantics-fixtures/violations` 含明文密钥、内网 IP、个人信息、指令注入、越界写盘、shell 调用，语义自检必须报出七项 FAIL。

写反向夹具的一条纪律：**夹具里出现的假凭据要一眼可辨是假的**。本项目的夹具用形如「示例假密钥，请勿使用」这类明确标注的值，并加注释说明是故意构造。既是给读代码的人看，也是防着自动 secret scanning 误报——一个长得像真密钥的字符串会让托管平台报警，是很烦的噪音。

## 第 6 章　召回：代理指标与真实行为的差别
这一章讲本项目里最容易被误解的一处。**代理测试通过不等于平台真实召回通过**，这不是免责套话，是两件测的东西根本不同。

### 6.1 两套指标测什么
**代理测试**（`check_triggers.py`）算的是字符二元组重合度。它测的是 description 在**词面上**是否覆盖了用户可能的说法。这个指标能发现的问题是结构性的：某个说法完全没在 description 里出现过、某类触发语只有术语型没有口语型。

它测不了的问题是语义性的：用户说的和 description 写的用词完全不同但意思一样（比如用户说"把这活儿收个尾"，description 写"整理待办事项"），词面重合度很低但真实召回是能命中的。反过来，词面高度重合也可能因为说的是完全不同的事。

**真实召回**由平台的调度算法决定。它可能用 embedding 相似度，可能用关键词匹配，可能用模型判断，也可能几种混用。本项目无法控制它怎么算。

所以两者的定位是：**代理测试是预检，真实召回是终检**。前者用来在交付前发现明显漏词，后者必须在真实环境里做。本项目的 README 与多处文档都坚持把这两者分开表述，不把代理测试的结果说成"召回已验证"。

### 6.2 真实召回实测怎么做
本项目做了一次真实召回实测，方法参照 skill-criticagent 的"有/无行为对比 + description 触发测试"规范。核心是**只给判断者 name 与 description，不给技能正文**——模拟平台技能目录里能看到的东西。

具体做法是派独立子 agent，每个只拿到 name、description 与自己负责的那批 query，不接触技能正文，也不接触其他 query 的答案。每条 query 独立判断三次，判定值只有 `skill-creator`（会激活）或 `none`（不激活）。最终结果：17 条 query（6 条正样本、11 条负样本）共 51 次独立判断，全部正确，0 误触发、0 漏触发、0 抖动。

这个实测里有一个插曲值得记：第一次测试集放错了——把另一个技能（待办索引）的触发语当成了本技能的正样本，四条被判 `none`。误判的是测试集，不是 description。**不能拿别的技能的触发语当本技能的负样本期望值**，期望值必须按职责边界逐条论证。

### 6.3 把实测结果固化
实测结论如果只写进文档，过三个月 description 一改就失效了。所以本项目把它做成断言：`tests/recall-test/check_recall.py` 记录实测时的 description 指纹与每条 query 的判定记录。每次回归时校验两件事：description 指纹是否与实测时一致（不一致就要求重跑实测），判定记录自身是否自洽（三次判断一致、且与期望一致）。这样 description 一改，回归立刻失败并提示"实测结论不再适用"。这是把一次性测量变成持续约束的做法。

### 6.4 实测的已知边界
判定是模型自报的，不等于平台调度器的实际行为。平台可能用 embedding 相似度而非模型判断，两者会有差异。另外本项目当前只有一个技能包，没有测过多技能竞争场景——同一目录里若有多个职责相近的技能，误触发风险会上升。最后，17 条 query 覆盖常见说法形态，无法穷举真实用户表述。这些边界都写进了 `tests/recall-test/README.md`，没有把它们包装成"已验证平台召回"。

## 第 7 章　需求采集：信息在一处采集、三处使用
环节二产出的八字段需求卡，是整条流水线里信息密度最高的产物。它的特点是**同一份信息在三个地方被用**，这决定了字段的设计。

### 7.1 八个字段与它们的去处
| 字段 | 内容 | 用在何处 |
| --- | --- | --- |
| ① 服务对象 | 谁会用 | 环节三的场景句、环节五的语体 |
| ② 真实场景 | 多久一次、什么对话里 | 环节三的场景句、环节二的可判定性 |
| ③ 触发原话 | 三类各 ≥3 条 | 环节三的 description、环节六的正样本 |
| ④ 目标产出 | 文件名 + 类型 + 必含字段 | 环节四的目录决策、环节五的输出示例、环节六的产出抽样 |
| ⑤ 关键约束 | 固定口径、顺序、格式 | 环节三的可识别对象、环节五的前置段 |
| ⑥ 不做什么 | 能力/场景/判断三类排除 | 环节三的排除句、环节六的负样本、环节五的禁止项 |
| ⑦ 相邻易混淆需求 | 任务 + 归属去向 | 环节三的排除句归属、环节六的负样本 |
| ⑧ 待确认项 | 确认什么 + 不确认后果 + 当前默认 | 环节五的标注、交付物的待确认项 |

同一个字段在多处使用时，口径必须一致。举例说，需求卡第 ④ 项写"产出 `feedback-triage.md`，字段：编号、原文、类型、优先级、责任组、建议动作"，那么环节五的输出示例字段表必须与这六项一致，环节六的产出抽样也按这六项核对。三处若不一致，交付出去的技能就会"看起来完整但少了一个字段"——而这种错误在初次使用时很难被发现。

### 7.2 不做什么的三类划分
第 ⑥ 项要求分三类填写，这个划分不是形式主义，三类的处理方式不同。

**能力不做**：写清本技能做不到什么，以及替代路径。"不覆盖 issue 自动创建"——这句话让用户知道边界在哪。

**场景不做**：写条件可判定的不出手场景。"当输入不是代码仓库时不处理"比"不适用于其他场景"有用得多，后者无法判定。

**判断不做**：写必须由人拍板的事项。"产出不构成专业意见，需人工复核"属于这一类。Skill 能给判据，但不该替人做决定。

这三类在 description 的排除句里会被压缩成一句话，在环节五的禁止项里会展开成具体动作。压缩时不能丢判断不做那一类——那是最容易在追求简洁时被砍掉的，砍掉之后技能就变得越权了。

### 7.3 推断项的标注
需求卡里非用户明说的内容要标"推断"。比如用户说"帮我整理会议记录"，输出文件名、字段结构、判定优先级都是推断出来的。标推断的意义在于让人类确认时知道哪些是用户明确要的、哪些是 AI 自己补的。人类确认八字段时，重点看推断项——那些是 AI 最容易理解偏的地方。没标推断的内容会被当成用户要求，读起来就顺，错了也发现不了。推断项在交付时若仍未确认，出现在待确认项里，写清"确认什么 + 不确认的后果 + 当前默认取什么"三要素。第三项最容易被漏——不写当前默认，人类就没法判断这个待确认项是否阻塞交付。

### 7.4 两轮采集的顺序
两轮采集有先后不能颠倒的原因。第一轮只问触发相关，因为触发原话是最难补的信息——它必须来自用户真实说过的话，一旦开始问"你会怎么开口"，用户很容易给出规范化的书面表述（"请生成一个客户反馈归类报告"），这种话作不了触发语。真实场景里的说法是"帮我把这些反馈分一下类"。第二轮才问交付与边界，因为交付形态依赖对任务的理解，第一轮没问清任务就问产出会得到空泛答案（"一份反馈表"），这种答案无法验收，违反可判定产出原则。每轮最多三问。问多了用户会烦，烦了就会随便答，随便答的需求卡不如没有。

## 第 8 章　目录决策与渐进披露
技能包加载时，主文件会被完整读入上下文，references 里的文件只在明确指向时才读。这个机制叫渐进披露，它决定了文件该怎么组织。

### 8.1 三问判定与理由标准
环节四的三问决定要不要建目录：

| 判定问题 | 答"是"则 |
| --- | --- |
| 有大量细节用到才读，放主文件会挤占常驻上下文？ | 建 `references/`，按单主题拆分 |
| 有确定性操作要可复现？ | 建 `scripts/` |
| 有要复制填充的模板？ | 建 `assets/` |

第一问的判定标准是"单段内容超过主文件预算 15%，或只在某一步加载"。按比例算比按绝对行数算准。第二问的"确定性操作"指的是结果必须逐次一致的逻辑。举例：一个技能里写着"按以下规则给待办分级：P0 是崩溃类、P1 是性能类、P2 是体验类"。这段逻辑如果写在正文里，模型每次执行可能给出略有差异的分类结果；写成脚本，每次跑出来完全一致。**同样的内容，位置决定了它是"建议"还是"保证"**。

第三问的"复制填充"要严格理解：给产出物复制用的模板，而不是给模型读的说明。需求卡空白模板属于 assets（人要填），方法论说明属于 references（模型要读）。

### 8.2 理由不合格就删目录
每个非默认目录要写一句理由，格式是 `[路径] → 不能放主文件的理由 + 加载/执行时机`。关键在于理由必须**可判定**。四个不合格表述："更规范""惯例""更专业""方便扩展"。这些词无法回答"那什么时候可以直接放主文件"，所以判不合格，处置是删掉目录回最小集重新问三问。写不出合格理由，说明这个目录本来就不该建。这是三问机制真正起作用的地方——它逼着做减法。多数技能的最终形态是只有 SKILL.md 或 SKILL.md + 一个 scripts/，而不是四个目录全建。

### 8.3 行数预算怎么算
预算表按段落估行再相加：

| 段落 | 行数区间 |
| --- | --- |
| 目标段 | 12–18 |
| 前置段 | 20–30 |
| 步骤段 | 每步 14–22 |
| 输出示例 | 18–28 |
| 禁止项与常见错误 | 25–35 |
| 资源索引 | 8–12 |

目标 ≤300，上限 500。超 300 定位超支段只外置该段；超 500 必须拆成多个单主题 references。单个 reference 同样有预算：目标 ≤300 行，上限 500 行，且一个 reference 只讲一件事。这套预算是按"主文件常驻上下文"算的。300 行的主文件对大多数模型来说已经是不小的常驻负担，而用户在一次对话里可能同时有几个技能处于激活状态。本项目的 skill-creator 主文件现在 132 行，远低于预算，就是这个道理——**方法论细节放 references 按需加载，主文件只留路由与关键约束**。

### 8.4 资源索引是必需项
主文件必须有一张资源索引表，写明每个文件什么时候加载。P012 专门检查这一项。这不是文档洁癖。没有索引表，模型无法知道包里还有什么、什么时候该去读。技能退化最常见的表现就是"这个技能明明有相关功能，但模型没去读那个文件"——因为正文没告诉它那里有什么。索引表的三列是：路径、用途、加载时机。加载时机要具体到环节或步骤编号，"S5 执行时"比"需要时"有用得多。

## 第 9 章　正文规格：六段骨架与四要素
正文是技能真正执行时的依据。它写得好不好，直接决定产出质量。本项目的正文规格有三层：段落的骨架、步骤的要素、语言的判定性。

### 9.1 六段骨架及其顺序
顺序固定：目标 → 前置 → 步骤 → 输出示例 → 禁止项 → 常见错误。目标段把输入转成什么可验收产出，单段、动词开头、≤2 行。不合格的表现是段内有背景叙述或愿景句——"本技能旨在提升团队协作效率"这种句子没有验收形态。前置段分两部分：开工必拿信息（每项有来源或获取方式，缺项有处置）、按需加载资源、运行环境。缺项处置必须写清楚，否则 AI 遇到缺项时会自己编一个。

步骤段是主体，每步四要素。输出示例段给文件名、必含字段表、字段说明，并要有一段真实成品片段——片段里不能有占位标记，写"示例略"等于没写。禁止项段是本技能明确不做的动作，每条能对应一次真实误操作。常见错误段是三栏表：症状、根因、最小修复，至少三行，症状要可观察。

### 9.2 四要素里的失败分支
输入、动作、产出三项是常规要求，失败分支是本项目规格里最吃重的一项。失败分支的格式是：当 `[可观测条件]` 成立时，退回 `[环节或步骤]`，补 `[文件 / 字段 / 结论]`。它为什么吃重：一个只会成功路径的技能，遇到异常时模型会自己发挥。输入文件缺失，模型可能编一个；格式不对，模型可能硬解析；某个判定卡住，模型可能跳过继续往下。这些行为在产出里表现为"看起来完成了但其实不对"，而使用者在事后很难追溯。有了失败分支，异常的处理变成流程内可预期行为：输入缺失就退回采集并列出待确认项，格式不对就退回上一步并说明缺哪个字段。

判定标准很直白：**该步单独交给另一个 AI、不给其他上下文仍可执行**。做不到就重写该步。这条标准能自动暴露"这步依赖前面步骤的某个结论但没写出来"的问题。

### 9.3 模糊词替换表
六个模糊词各有固定替换格式：

| 模糊写法 | 替换格式 |
| --- | --- |
| 必要时 [动作] | 当 [可观测条件] 成立时，执行 [动作] |
| 酌情 [选择] | 按 [表名或规则名] 对应行选择 [结果] |
| 视情况 [调整] | 按 [阈值或字段] 判定：达到 [阈值] 取 A，未达到取 B |
| 灵活处理 [对象] | [对象] 缺失且影响 [产出] 时，先问 1 轮（≤3 问）；仍缺则标「待确认」 |
| 适当 [调整] | 按 [精度 / 量级 / 上限] 写明取值依据后执行 [动作] |
| 根据实际情况 [动作] | 按 [分类表] 第 [N] 类处置，不按主观判断 |

替换后条件句必须能判真假。判不了假就是没写清，按第 6 节的失败分支退回重写。"灵活处理"的替换格式值得单独说：它给了「先问 1 轮（≤3 问）」这个上限。问一轮是必要的——有些信息模型可以推断，有些必须问用户。不给上限，模型可能连续追问十轮把用户问烦；给得太死（不许问），模型会编。

### 9.4 语体五条与一处定义
祈使句：句子以动词或动作短语开头，句首不出现主语、判断句或描述句。无主句：第二人称代词与自称代词零出现。这一条在教程类文档里最难遵守，因为教程天然要说"你"。无营销词：宣传性形容词与空泛评价词零出现。要用形容词替代判定条件。一处定义：同一字段、路径、规则只在一处定义，主文件与 references 不双写。双写意味着两处可能不同步，而读者读到哪一处就用哪一处。

编号规则：S1…Sn 连续，不跳号，不设 S0，编号只在本技能包内有效。

### 9.5 占位符与槽位残留
交付前双花括号占位标记零残留，判定口径是 P007 报 FAIL 即未通过（判据细节见第 5.1 节）。模板文件自身的花括号标记不参与检查，但复制到产出技能包后必须全部替换。替换规则是：花括号包住的字段名，替换为该技能包内的真实文件名、字段名或取值；无真实取值的删除占位符并补写判定条件，不留空位。"不留空位"这句是重点。删除一个占位符容易，但删掉之后那一行的语义就空了。正确做法是删除的同时补上判定条件，让这一行仍然可执行。正文引用资源只写相对技能根目录的路径。绝对路径与工作区相对路径都会被 S007 拦下。

### 9.6 常见错误表怎么写
三栏表的价值在于最后一栏"最小修复"必须可执行：

| 症状 | 根因 | 最小修复 |
| --- | --- | --- |
| 输出条目优先级全是 P2 | 正文不含 P0–P3 / URGENT / HIGH / LOW 关键字 | 检查 S3 判定规则是否加载；给原始命中条目手动标注优先级关键字后重跑 |

这行的症状是可观察的（看产出就能发现），根因落到了具体步骤（S3 判定规则），修复动作是动词开头且指明了复核方式（重跑）。相比之下，"优先级判定有问题，应检查相关逻辑"这样的写法没有可操作性。写不出好的常见错误表，通常说明正文本身写得不够具体——错误种类写不出来，是因为错误还没被具体化。

## 第 10 章　工程教训集
本章记录本项目开发过程中真实踩过的坑。每一节都是已经付出过代价的结论，改动本项目前应当先读。这些坑的共同特征是：**它们不会让程序报错，只会让判定悄悄失准**。

### 10.1 判据退化成永真通过
这是本项目最危险的一类缺陷，因为它看起来在工作。具体经过：负样本误触发检测最初的设计是"负样本得分 ≥ 正样本最低得分即判误触发"，用相对阈值看起来比固定阈值合理。但正样本的说法直接取自 description 的触发语，纯覆盖率必然等于 1，于是基线恒为 1.0，**任何负样本都判不了误触发**。测试跑起来是绿的，输出"负样本 5/5 未误触发"，但这个结论没有任何信息量。

发现方式是加了反向夹具：一个 description 用词宽泛、负样本与它高度重叠的技能包。这个夹具如果恒定通过，就说明判据退化了。回归检查器因此加了一条硬断言：反向夹具必须报出误触发，恒定通过则回归 FAIL。教训：**任何"通过率很高"的判定都要有一个必须失败的对照**。没有反向夹具的检测器，它的通过率没有意义。

### 10.2 检查器扫自己
第二个坑同样隐蔽。语义自检脚本 `check_semantics.py` 里定义了敏感词的正则模式，其中包含系统配置目录与 SSH 密钥目录的字面量。结构校验 S010 扫描 scripts/ 下的文件，扫到检查器自己的源码，判定"含敏感系统路径"，FAIL。同一类问题还有：`check_semantics.py` 里 import subprocess（编排校验脚本的正常依赖）被第 28 项判成"引入子进程模块"，进而 FAIL；`health_check.py` 调用子脚本被同样判违规。

三处修法不同但思路一致：**检查器不检查自己**（扫描时排除自身文件）；**模式字面量分段拼接**（把敏感路径拆成两段再拼起来，这样扫描器扫到这个文件时不会命中自己的规则，这是 `validate_structure.py` 里早就有的做法，本项目沿用了同一手法）；**合法用法不算违规**（subprocess 编排同包脚本是合法的，判据改成"有无 shell 调用与 `shell=True`"）。教训：**校验器的源码本身是校验对象的输入**，设计时必须假设自己会被扫到。

### 10.3 否定语境误伤
规则说明句里的敏感词被当成违规内容。`self-check.md` 里写着"不绕过鉴权、不诱导批量注册与刷量"，语义自检第 21 项（敏感内容零命中）把"绕过监管"判成了违规。修法是加否定语境豁免：命中所在行含否定标记（不、禁、无、非、勿、排除、拒绝、防止、避免、不得、不能）即豁免。豁免的判据一开始设成"命中位置前 12 个字符内出现否定标记"，仍然误判——那句里的"不"离命中位置较远。改成行级判断后正常。教训：**语义类判定的上下文边界要放宽到足以覆盖真实的语用形态**。宁可放过一些真违规（人工能补），也不要误杀规则说明（会让人不敢写规则）。

### 10.4 误判与漏判的连锁
修 10.3 的过程中引出了新的问题。身份证号是 18 位数字，同时匹配了 16–19 位的银行卡模式，同一串数字被报成两种问题。修法是银行卡模式排除已被识别为身份证号的形态。

另一个方向的漏判：写盘路径越界检测只看写盘调用那一行，而违规路径可能写在变量里（先给变量赋一个用户主目录下的绝对路径，再调用写入函数）。只看调用行会漏。修法是增加模块级常量追踪：扫出常量里的绝对路径或上跳路径，再回溯哪些写盘调用引用了它。教训：**检测器与被检测对象的表达方式之间存在缝隙**。写检测器时要预想几种等价写法，每种都要能命中。

### 10.5 朴素子串匹配
P007 最初的实现是查正文里有没有 `TODO` 子串。这在真实场景里立刻出问题：一个扫描待办注释的技能，产出文件名必须叫 `TODO-INDEX.md`，正文必须列出六种标记词（含 TODO）。朴素检查把这些全判成残留，第一次产出必然 FAIL。朴素实现的诱惑在于它简单。但简单在这里等于错误。修法是改成槽位式判定（详见第 5.1 节），判语法位置而非子串出现。

同类的还有 S004 的文件名检查：最初用 `\b(todo|placeholder|example)\b` 匹配文件名，把 `find_todo.py`、`example-config.json` 这类正常命名误判成占位文件。修法是改为文件名主干整词判定——取 `path.stem`（去掉扩展名）再与占位词整词比较。教训：**词表类判定的精度取决于匹配粒度**。整词、词干、位置、上下文，每一层都比上一层更准，但也更容易漏。选哪一层取决于误判与漏判哪个代价更高。

### 10.6 排除句抬高召回得分
负样本算分时用了整条 description，导致排除句里的词被算作召回依据。"帮我登录这个账号"因排除句里的"账号授权"被判误触发（0.429）。修法是截掉排除句再算（详见第 5.2 节）。修完降到 0.286。教训：**排除句的存在目的与召回计算的目的相反**。任何用 description 全文做匹配的场景，都要考虑是否该先剔除排除句。

### 10.7 硬编码行号的断言
回归检查器里断言"安全夹具的 S011 报错必须在第 3 行"。这个断言的本意是"注释行里的同形态字样不该被计入"，但写成硬编码行号后，夹具文件一改行就失效——改夹具时忘了改断言，回归就红了，红的原因是断言过时而不是代码有问题。修法是动态求出违规行号：扫夹具里第一个含违规形态且非注释的行，把这个行号作为期望值。这样夹具内容可自由调整，而断言的语义（注释行被排除）始终被验证。教训：**断言要断言语义，不是断言字面值**。硬编码的期望值是回归的隐性维护负担。

### 10.8 判据选择的第一直觉常常是错的
回顾本章出现的三个判据设计：相对阈值（正样本最低分）→ 失效，退化为永真通过；排除句参与算分 → 方向相反；固定阈值 0.40 → 有效。第一个直觉"用相对阈值更自适应"听起来更有道理，但正样本的构成决定了它必然为 1。**判据的设计要基于数据的实际分布，而不是基于方法的优雅程度**。本项目踩过的坑里，有一半是"听起来更合理的做法"导致的。因此每个阈值改动、每个判据改动，都必须配套一个反向夹具和一个正向夹具，两个夹具一起跑才能确认改动既没让检测器变瞎，也没让它变得过度敏感。

### 10.9 文档口径与代码口径必须一致
项目里出现过文档说一套、代码做另一套的情况：self-check.md 的第 7 项列了一串残留词，但代码出于避免误报的考虑并不检查其中几个；又写着判定依据是结构校验 S004，实际依据是内容校验 P007。这类不一致的危害在于：读者按文档理解校验器，会得出错误结论；改动时按文档理解也会改错地方。

修法是每次改判据时同步改文档，把依据的脚本名与项号写清楚。本项目现在的做法是文档里直接写"判定口径为内容校验 P007 报 FAIL 即未通过"这种可执行的表述。另一个相关问题：历史记录里保留了旧包名 `news/`。改写历史记录会失真，不改会误导。折中是保留原文、在文件顶部加一条包名沿革说明，指出早期批次的包名与当前包名的对应关系。

### 10.10 缓存产物污染包体
Python 运行脚本会生成 `__pycache__` 目录与 `.pyc` 文件。这些是运行时产物，不属于技能包内容，但它们会被结构校验的"死文件检查"当成未被引用的运行文件，也会让行数清单读取时因编码问题报错。三重修法：回归检查器的死文件检查与行数清单排除 `__pycache__` 与 `.pyc`；项目根加 `.gitignore` 排除这些产物；跑校验时设 `PYTHONDONTWRITEBYTECODE=1`。教训：**工具链自身产生的产物必须显式排除**。这类问题在第一次出现时很莫名，因为报错信息完全指不到原因。

## 第 11 章　改动本项目时的约束
给后续维护者的操作清单。每条都对应一个已知的、会造成实际损害的改法。

### 11.1 改校验脚本前
先确认新判据有没有反向夹具。没有就先写夹具，再写判据。夹具必须能在判据有 bug 时报出与正常情况相反的结果——如果夹具在判据退化时也通过，它就失去了保护作用。改动语义类判定时，检查它是否会扫到自己的源码。检查器源码里的模式字面量、import 语句、正则表达式都可能被自己的规则命中。既有做法是分段拼接字面量。改动阈值时，检查是否有依赖该阈值的其他判定。本项目里命中阈值 0.30 与负样本混淆阈值 0.40 是两个独立概念，改一个不影响另一个；这需要在改动时确认，不是自动保证的。

### 11.2 改 description 后
description 是唯一检索入口，改它影响面比改正文大得多。改完必须做三件事：跑 `check_triggers.py` 确认正负样本都正常；跑 `tests/recall-test/check_recall.py`，它会因为指纹变化而失败，此时重跑真实召回实测并更新 `EXPECTED_DESC_SHA` 与 `decisions.json`；检查召回实测的 query 集是否需要新增说法。

**不要为了让某个测试通过而修改期望值**。期望值错了一律是测试错，不是测试代码对。

### 11.3 改正文时
主文件行数上限 300 是硬约束。当前 132 行，还有余量，但新增内容前先想清楚该放主文件还是 references。判断标准是"这段内容只在某一步加载吗"——是则外置。新增外置文件后必须同步三处：主文件的资源索引表（否则 P012 或 S006 会拦）、skill-creator 包内对应的方法文档（否则流程与实现脱节）、本教程的相关章节（本教程要反映当前实现，不反映历史实现）。

### 11.4 加新校验项
加项之前先回答：这项能被脚本判定吗？如果需要理解业务内容、需要跨文件比对、需要平台外部信息，那它属于人工清单，写进 skill-creator 包内的自检清单文档而不是写成脚本。写成脚本的项必须给出证据形式（文件 + 行号 + 计数），不能只给"通过/不通过"。`check_semantics.py` 里每项都带证据，因为自检清单的总则要求"PASS 要有证据，只写通过不写证据的按不通过处理"。加完项要更新该清单文档里"已自动化的语义项"一节。

### 11.5 改完之后
跑 `python tests/feature_check.py`。这个回归检查器现在有 13 段：包体本体、安全夹具、结构夹具、内容校验 P007、引用与死文件、行数清单、流水线语气扫描、流水线结构检查、流水线走查、负样本检测、负样本判据检测力、语义项自检与反向夹具、召回实测回归断言、健康度体检。然后同步 `skill-creator/` 到 `dist/skill-creator/`，并验证逐文件哈希一致。dist 是要分发的那一份，回归固定校验它。

### 11.6 本项目不做的事
不覆盖平台 UI 操作与账号授权——写不了就别装。不覆盖复杂工程集成——需要接真实系统的技能，成本与本项目的方法论不在一个量级。不承诺平台真实召回——本项目能做的是让 description 贴近真实说法并提供代理测试，真实召回由平台算法决定。不把脚本判定当成全部——四套校验全过只说明形态与表述合规，说明不了业务逻辑对。业务正确性由使用者判断，体检的边界一节里明确写了这一点。

## 第 13 章　一句话收束
这个项目真正的产品不是那六个脚本，也不是那份 132 行的主文件，而是**一套把"我觉得没问题"换成"这里有证据"的判定习惯**。写脚本只是把这种习惯固化下来。真正难的是接受一件事：一个自己写的检测器，凭什么相信它没坏。答案是反向夹具、动态断言、双向验证，以及每次改判据时都问一句"我怎么知道这次改动没让检测器变瞎"。
